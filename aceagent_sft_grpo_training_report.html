问题（Question）

本报告回答一个工程复盘问题：如何从 AceAgent/RLSandbox 的朴素 fine-tune + eval 起步，逐步通过数据改造、native tools 协议、schema-aware reward、tool restraint 数据和 8B/32B GRPO，提升一个 agent 模型对本项目机器人与工具调用环境的适配度？

这里的“适配度”不是泛泛的聊天能力，而是面向生产式 agent 的四类能力：正确选择工具（tool selection）、正确填写参数（argument grounding）、避免越权副作用（side-effect safety）、以及在项目机器人/浏览器/跨源任务之间保持协议边界（protocol and domain separation）。

背景与动机（Background & Motivation）

AceAgent 的核心业务场景是让大模型在 OpenAI-compatible tools / PydanticAI tools / 项目内机器人工具之间进行稳定的多步决策。普通 base model 即使会“讲”工具，也常常无法满足实际系统的硬约束：它可能伪造工具名、漏掉关键参数、在需要澄清时直接执行副作用工具，或者在浏览器 UID、机器人坐标、订单 ID 等必须精确 grounding 的字段上胡编。

因此工作不是一次性“训一个模型”，而是沿着下面的反馈闭环推进：

  1. 先建沙盒和 eval，知道模型在项目任务中能不能按工具序列完成任务。
  2. 用朴素 SFT 获得工具调用格式、项目机器人任务和通用 tool-call 的初始能力。
  3. 发现 SFT 对安全边界和多步策略不够强，于是加入 reward-shaped continuation，再升级为 online GRPO。
  4. 发现 reward 容易被“只不犯禁但不做事”或“参数不对但格式像”钻空子，于是改成 schema-aware reward。
  5. 发现模型有过度执行倾向，于是加入 tool-restraint 数据和惩罚边界；同时观察 8B 与 32B 在 SFT/GRPO 上的收益差异。

这个过程符合 agent post-training 的常见规律：SFT 负责把模型拉到“会按协议做事”的局部流形，RL/GRPO 负责在同一任务输入下通过多候选采样比较，优化那些无法只靠 next-token imitation 表达清楚的策略偏好。

基础概念与术语

监督微调（Supervised Fine-Tuning, SFT）

SFT 用人工或程序构造的目标输出监督模型，使其学会项目规定的消息格式、工具名、参数结构和回复风格。对 AceAgent 来说，SFT 的价值是“把 base model 拉进工具协议”，尤其是 OpenAI function/tool call JSON、Qwen3-VL native tools 模板、机器人工具 schema 与浏览器 deferred action schema。

强化学习（Reinforcement Learning, RL）与 GRPO

强化学习把模型输出视为动作（action），由奖励函数（reward function）评价轨迹好坏。GRPO（Group Relative Policy Optimization，组相对策略优化）在每个 prompt 下采样多个 completion，通过组内 reward 标准化估计 advantage，减少对 value/critic 模型的依赖。DeepSeekMath 提出 GRPO 用于 LLM 后训练，TRL 也提供 GRPOTrainer 的工程实现说明。

工具调用（Tool / Function Calling）

工具调用是让模型输出结构化函数名与参数，由外部系统执行。PydanticAI 文档把 function tools 解释为模型可调用的外部动作/检索接口；AceAgent 本地用 server/tools/registry.py 把项目工具注册成 PydanticAI Tool，并用 native tools eval 校验 Qwen3-VL 模板中真实 tools=tools 协议，而不是把工具 JSON 手写进 prompt。

具身智能与机器人任务

机器人任务不仅是文本工具调用，还涉及实体状态、地图、坐标、导航进度、任务取消和副作用控制。基础概念包括观测（observation）、动作（action）、状态（state）、轨迹（trajectory）和环境反馈（environment feedback）。在本项目中，沙盒把真实机器人执行接口替换成可模拟的状态机，从而在不触碰真实硬件的情况下评估导航、拍照、购买、停止、返航等行为。

RLSandbox/AceAgent 沙盒能力

本地 server/agent/sandbox.py 是整个训练评测闭环的起点。它不只是 mock 工具返回值，而是把 agent run 过程中的工具调用、模型 tool call、final text、虚拟机器人状态、地图点、订单状态和 timeline 都记录下来，再按预期轨迹打分。

沙盒评分信号

沙盒结果不是单一 pass/fail，而是由序列、参数、禁用工具、最终文本、状态检查和行为检查组成。抽象地说，单个 case 的 loss 可写为：

\[ \mathcal{L}_{case} = w_s L_{seq} + w_a L_{args} + w_f L_{forbidden} + w_t L_{text} + w_x L_{state} + w_b L_{behavior} \]

变量解释：\(L_{seq}\) 表示工具顺序错误，\(L_{args}\) 表示参数错误，\(L_{forbidden}\) 表示调用了 forbidden tools，\(L_{text}\) 表示 final answer 没有覆盖必要语义，\(L_{state}\) 和 \(L_{behavior}\) 来自虚拟状态与行为检查。实现映射：这些信号对应 sandbox.py 中的 trace、state timeline、behavior checks 与 summary loss；本地早期 eval 以 max_loss 和 pass rate 汇总。

评测指标数学定义

对一个 suite \(D=\{(x_i, y_i)\}_{i=1}^{N}\)，工具名准确率可写为：

\[ \mathrm{ToolAcc} = \frac{1}{N}\sum_{i=1}^{N} \mathbf{1}\left[ \mathrm{name}(\hat{c}_i)=\mathrm{name}(c_i^\star) \right] \]

变量解释：\(x_i\) 是第 \(i\) 个 prompt，\(y_i\) 是 gold trajectory，\(\hat{c}_i\) 是模型预测的工具调用，\(c_i^\star\) 是参考工具调用。实现映射：native tools eval 报告中的 tool_acc 对应该类工具名匹配，multi-step 时结合 required coverage 评价。

关键字段准确率只看影响执行安全和 grounding 的字段：

\[ \mathrm{CriticalExact} = \frac{ \sum_i \sum_{f\in \mathcal{C}(t_i)} \mathbf{1}\left[\hat{a}_{i,f}=a^\star_{i,f}\right] }{ \sum_i |\mathcal{C}(t_i)| + \epsilon } \]

变量解释：\(\mathcal{C}(t_i)\) 是工具 \(t_i\) 的 critical fields，例如 robotId、taskId、订单 ID、SKU、browser uid/target、坐标和枚举字段；\(\epsilon\) 防止空分母。实现映射：schema_aware_reward.py 与 schema-aware eval 对这些字段执行严格或受控容忍匹配。

数学形式与训练目标

SFT 目标

令 \(x\) 表示用户消息、系统提示、历史和工具 schema 组成的输入上下文，\(y=(y_1,\ldots,y_T)\) 表示目标输出 token 序列。SFT 最小化 next-token 负对数似然：

\[ \mathcal{L}_{\mathrm{SFT}}(\theta) = -\mathbb{E}_{(x,y)\sim D_{\mathrm{SFT}}} \left[ \sum_{t=1}^{T} m_t \log \pi_\theta(y_t\mid x,y_{1:t-1}) \right] \]

变量解释：\(\theta\) 是模型参数，\(\pi_\theta\) 是策略模型，\(m_t\) 是 loss mask。实现映射：对工具调用训练，assistant/tool-call token 计入 loss，用户/system/tool schema 本身通常作为条件上下文；v1 用 LoRA 更新部分参数，v2/32B 阶段更新 full language parameters 并冻结 vision modules。

GRPO 组相对优势

对同一 prompt \(x\)，采样 \(G\) 个候选输出 \(y^{(1)},\ldots,y^{(G)}\)，用奖励函数 \(r_i=R(x,y^{(i)})\) 打分。组内标准化 advantage 为：

\[ A_i = \frac{r_i-\mu_r}{\sigma_r+\epsilon}, \quad \mu_r=\frac{1}{G}\sum_{j=1}^{G}r_j,\quad \sigma_r=\sqrt{\frac{1}{G}\sum_{j=1}^{G}(r_j-\mu_r)^2} \]

变量解释：\(G\) 是每个 prompt 的生成数，本项目 8B online GRPO 使用 num_generations=8；\(\mu_r\)、\(\sigma_r\) 是组内均值和标准差；\(\epsilon\) 防止除零。直觉：同一个任务下，不看绝对分，而看哪个候选比同组候选更好。实现映射：训练脚本按 group reward 生成 advantage，再做 PPO/GRPO 风格策略更新。

带 KL 约束的 GRPO surrogate

本项目 v2 GRPO 从 SFT checkpoint 初始化，并使用低权重 reference KL。一个简化的 token-level 目标可写为：

\[ \mathcal{L}_{\mathrm{GRPO}}(\theta) = -\mathbb{E} \left[ \sum_{i=1}^{G}\sum_{t} \min\left( \rho_{i,t} A_i, \mathrm{clip}(\rho_{i,t},1-\epsilon_c,1+\epsilon_c)A_i \right) - \beta D_{\mathrm{KL}}\left( \pi_\theta(\cdot\mid s_{i,t}) \,\|\, \pi_{\mathrm{ref}}(\cdot\mid s_{i,t}) \right) \right] \]

变量解释：\(\rho_{i,t}=\frac{\pi_\theta(y^{(i)}_t\mid s_{i,t})}{\pi_{\mathrm{old}}(y^{(i)}_t\mid s_{i,t})}\) 是重要性比率，\(\epsilon_c\) 是 clip 范围，\(\beta\) 是 KL 权重，\(\pi_{\mathrm{ref}}\) 是 SFT reference policy。实现映射：v2 报告记录 KL beta = 0.003、reward scale = 0.5，目的是在提升 reward 的同时不要偏离 SFT 工具协议太远。

Schema-aware 奖励

最终 reward 不是单一匹配，而是多个组件加权加 hard penalties：

\[ R(x,y) = \sum_{k=1}^{K} w_k\,c_k(x,y) - \sum_{\ell=1}^{L}\lambda_\ell\,p_\ell(x,y) \]

变量解释：\(c_k\) 包括工具名、顺序、coverage、critical argument、semantic argument、final contains、state success、scope 等正向组件；\(p_\ell\) 包括 forbidden tool、执行工具误调用、浏览器/项目工具混用、缺少必需参数、约束任务中调用工具等惩罚。实现映射：schema_aware_reward.py 按 AceAgent server/tools/*.py schema 解析并评分。

def grpo_step(prompt_batch, policy, ref_policy, reward_fn, G=8):
    # 1. Sample G candidate completions per prompt under native tools protocol.
    groups = policy.generate(prompt_batch, num_generations=G, tools=aceagent_tools)

    # 2. Parse model outputs robustly, including dict, JSON string, and malformed calls.
    parsed_groups = [parse_tool_calls(y) for y in groups]

    # 3. Score each candidate with schema-aware reward.
    rewards = [reward_fn(prompt, y, calls) for prompt, y, calls in parsed_groups]

    # 4. Normalize rewards inside each group to get relative advantages.
    advantages = group_normalize(rewards)

    # 5. Compute clipped policy-gradient loss plus small reference KL.
    loss = clipped_surrogate(policy, groups, advantages) + beta * kl(policy, ref_policy)

    # 6. Backpropagate through completion tokens only; log reward components for audit.
    loss.backward()
    optimizer.step()
    optimizer.zero_grad()
    return loss, rewards

总体结构：规则 reward + reference KL/LogP 约束

本项目的 GRPO 奖励不是训练一个单独的神经奖励模型（reward model），而是用规则奖励（rule-based reward）直接评价每个候选 completion，再用组内相对 advantage 推动 policy 更新。为了防止 policy 为了钻规则 reward 而偏离 SFT 学到的 native tools 协议，训练脚本还加载 SFT checkpoint 作为 reference model，在 completion token 上加一个低权重 reference regularization。本地 v2 run 使用 reward_scale=0.5、reference_kl_beta=0.003、num_generations=8。

从训练目标看，最终优化量可以分成两层：第一层是规则 reward 给每个候选输出打分；第二层是 GRPO policy loss 用这些分数构造组内 advantage，并加上 reference loss：

\[ \mathcal{L}_{\mathrm{train}} = \mathcal{L}_{\mathrm{GRPO}}\!\left( A(R_{\mathrm{rule}}(x,y)) \right) + \beta_{\mathrm{ref}}\, \mathcal{L}_{\mathrm{ref}}(\theta,\theta_{\mathrm{ref}}) \]

变量解释：\(R_{\mathrm{rule}}(x,y)\) 是 schema_aware_reward.score_candidate() 输出的规则分数；\(A(\cdot)\) 表示同一 prompt 下 8 个候选的组内标准化 advantage；\(\beta_{\mathrm{ref}}\) 是 reference loss 权重，本地 run 为 0.003；\(\theta_{\mathrm{ref}}\) 是 SFT reference model。实现映射：train_grpo_online.py 在 compute_loss() 中先生成候选、解析工具调用、调用 reward，再计算 clipped policy loss 和 reference loss。

规则 reward 的组成：组件加权 + hard penalty

规则 reward 的核心形式是组件加权求和再加硬惩罚：

\[ R_{\mathrm{rule}}(x,y) = s \left( \sum_{k\in \mathcal{K}_{f(x)}} w_{f(x),k}\,c_k(x,y) + \sum_{\ell\in \mathcal{P}} p_\ell(x,y) \right) \]

变量解释：\(s\) 是 reward scale，本地 v2 为 0.5；\(f(x)\) 是任务族（task family），例如 project_robot_task、browser_deferred_task、clarification_before_action；\(c_k\in[0,1]\) 是规则组件；\(w_{f(x),k}\) 是对应任务族权重；\(p_\ell\le 0\) 是 hard penalty。实现映射：reward_spec.json 中的 weights_by_task_family 提供 \(w\)，hard_penalties 提供 \(p_\ell\)。

这样的设计有三个目的。第一，规则 reward 可解释，每个候选为什么高分/低分都能写进 reward_components_rank*.jsonl。第二，不同任务族有不同重点：project robot 看 scope 和语义参数，browser deferred 看严格 UID/target 和不混用项目工具，clarification/restraint 看是否不调用工具并给出澄清/拒绝。第三，hard penalty 可以覆盖“只靠加权平均会被钻空子”的行为，例如 forbidden tool、忽略 robotId、执行工具误调用。

Reference KL / LogP loss：不是 reward，而是防漂移约束

训练中 reference 项不直接评价任务好坏，它约束新 policy 不要远离 SFT reference policy。实现上，脚本加载 --reference-model-path 指向 v2 SFT model；对同一 generated completion，分别计算当前模型 token log-prob 与 reference model token log-prob，然后在 completion mask 上计算平方差：

\[ \mathcal{L}_{\mathrm{ref}} = \frac{ \sum_{i,t} m_{i,t} \left( \log \pi_\theta(y_{i,t}\mid s_{i,t}) - \log \pi_{\mathrm{ref}}(y_{i,t}\mid s_{i,t}) \right)^2 }{ \sum_{i,t}m_{i,t}+\epsilon } \]

变量解释：\(m_{i,t}\) 是 completion token mask，只对生成部分计入；\(\pi_\theta\) 是当前 policy；\(\pi_{\mathrm{ref}}\) 是 SFT reference；\(s_{i,t}\) 是 prompt 加前缀生成 token 的上下文。实现映射：train_grpo_online.py 中 ref_loss = (((new_logps - ref_logps) ** 2) * completion_mask).sum() / denom，再执行 loss += reference_kl_beta * ref_loss。报告沿用“KL loss”称呼，但严格说本地实现是 log-prob L2 reference regularizer，功能上类似 KL 约束。

这个 reference 项的设计原因很实际：规则 reward 只能覆盖当前定义过的组件，不能完全刻画语言流畅度、native tools 模板稳定性、停止行为、已有 SFT 能力和未覆盖任务。因此如果没有 reference 约束，policy 可能为了拿高 reward 逐渐变成“奖励函数专用格式”，表现为输出过短、重复工具、过度拒绝、或牺牲通用 tool-call 能力。低 beta 让 GRPO 可以改变策略，但不会完全忘掉 SFT。

Reward 到 loss 的完整流

def compute_grpo_loss(prompt_batch, policy, ref_policy, reward_spec):
    # 1. For each prompt, sample G completions with native messages + tools.
    completions = policy.generate(prompt_batch, num_generations=8)

    # 2. Parse structured and latent tool calls robustly.
    parsed_calls = [parse_tool_calls(text) for text in completions]

    # 3. Rule reward: score tool sequence, critical args, semantic args,
    #    safety, restraint, scope, and hard penalties.
    raw_rewards = [
        score_candidate(row, text, calls, reward_spec)["score"]
        for row, text, calls in zip(rows, completions, parsed_calls)
    ]
    rewards = 0.5 * raw_rewards  # reward_scale from the v2 run.

    # 4. Group-relative advantage: compare candidates from the same prompt.
    advantages = normalize_within_prompt_group(rewards, group_size=8)

    # 5. Policy loss: clipped ratio objective on completion tokens.
    policy_loss = clipped_grpo_loss(policy, completions, advantages)

    # 6. Reference regularization: keep current log-probs close to SFT reference.
    ref_loss = masked_mean((policy.logps(completions) - ref_policy.logps(completions)) ** 2)

    # 7. Final objective. The local beta is 0.003.
    return policy_loss + 0.003 * ref_loss

为什么这套 reward 能修 v1，但还会留下 safety corner case

schema-aware rule reward 修复了 v1 最大的问题：旧 reward 过度奖励“没犯禁”和“final text 看起来合理”，新 reward 强制看工具名、顺序、coverage、critical fields、semantic fields 和 scope。因此 project_robot、browser_deferred、cross_source 的指标在 v3 明显上升。

但它仍然是 trajectory-level rule reward，不是环境真实执行后的 step-level verifier。对于 tau2 telecom 多故障任务，如果 gold 需要 5 个修复工具，模型只调用其中 1 个，coverage 组件会扣分，但其他组件如 no_forbidden、partial critical、final text 仍可能给分；这就是为什么 safety tool_acc/coverage 仍是 gate。下一阶段应把多步安全任务拆成 step-level reward 或 constrained coverage reward，使漏掉任一步都不能被“没有 forbidden”抵消。

边界修复前，真实 clarification_before_action rows 如果 reference trajectory 存在，执行工具调用仍可能拿到正向 restraint component。修复后，clarification rows 一律要求无 structured/latent tool call，并扩展 execution verb 检测。检查结果：good_score_mean 1.0000，bad_score_mean -5.3129，bad_cases_not_penalized 0。

逐组合深入解读

8B SFT v1 LoRA：先证明“数据能把模型拉进工具协议”

这一组合的设计目的不是追求最终最强模型，而是用低成本路径回答一个前置问题：公开 tool-use 数据、ARL-SCOUT 机器人数据、项目 sandbox 轨迹和 workflow safety 数据合在一起后，能不能把 Qwen3-VL-8B 从“会自然语言描述工具”推进到“能稳定输出项目可解析的 tool call”。LoRA + freeze vision 的训练模式降低了显存压力，也避免视觉塔在没有足够项目视觉数据时被无意义更新。

结果判断上，v1 SFT 成功建立了工具调用基线，但它的价值主要是协议学习（protocol learning），不是策略最优。它可以让模型知道 acerobotics_indoor_navigation、ToolSearcher、browser action 等工具名和参数长什么样；但遇到需要“先澄清再行动”“先查状态再取消”“副作用工具不能乱点”的任务时，SFT 的 imitation objective 不足以表达偏好强弱。典型 corner case 是模型能生成格式正确的工具调用，却会把不确定场景也当成可执行场景，或者在多步任务中只模仿最显眼的一步。

8B v1 GRPO-style：先验证 reward-shaped 数据是否真的有方向

v1 GRPO-style continuation 的设计目的，是在真正 online GRPO 尚未跑稳时，验证 RL/偏好数据是否能改善 project/safety。训练模式上，它不是严格的 online GRPOTrainer：本地报告明确记录这是把 GRPO/RL 数据 materialize 成 tool-call 轨迹后，用 known-good Trainer path 做 reward-shaped continuation。之所以这样设计，是因为当时 PeftModel adapter continuation + DeepSpeed/MACA 出现 NCCL 后 hang 和 0% GPU util，直接上完整 RL 会把问题混在“算法有没有用”和“训练栈跑不跑得动”之间。

结果很有诊断价值：project robot 和 safety side-effect 明显提升，说明数据方向有效；但 browser_deferred tool_acc 从 0.7188 掉到 0.3125，cross_source 从 0.8594 掉到 0.7109，说明偏好数据把模型推向 project/safety 局部最优。这个阶段的价值不是产出最终模型，而是证明“RL 数据有用，但如果不保护 browser 和 cross-source，会出现路线性遗忘”。具体 corner case 是 WebLINX/Mind2Web 的浏览器 UID/target 被模型伪造，hallucinated browser IDs 增多；这类字段不能靠语义相似度补救，因为点错 UID 就是点错页面元素。

8B v2 full SFT：从旧 prompt 协议切到真实 native tools

v2 full SFT 的核心不是“把 LoRA 换成 full parameter”这么简单，而是同时修复三个边界：第一，训练消息改成 Qwen3-VL native tools=tools；第二，数据改为 language-only，避免在没有真实视觉训练目标时污染视觉路径；第三，更新 full language parameters，让模型内部语言/工具路由有足够容量吸收 schema。freeze vision 不是保守参数，而是明确声明本阶段不训练真实视觉感知。

结果上，v2 full SFT/GRPO 把 project_robot 拉到 0.9923，说明 native protocol 对项目工具非常关键；但 safety 仍只有 0.2872，browser 只有 0.2484，表示仅仅换协议并不能解决 reward 粗糙和字段 grounding 问题。它的主要价值是成为 online GRPO 的可靠初始化点。corner case 是 project_robot 中 instruction/destination/instruction_en 历史字段 alias 曾经影响评分与训练一致性，后来 schema-aware eval 才把 semantic_navigation 的字段规则单独规范。

8B v3 full GRPO schema-aware：主线最有效的 8B 策略优化

这一组合是 8B 主线的关键阶段。设计目的从“学会工具格式”转向“在多个候选工具轨迹中选更符合 schema、安全和项目边界的轨迹”。训练模式采用 online GRPO、每个 prompt 采样 8 个候选、低权重 KL 约束到 SFT reference。这样设计的原因是 tool-use agent 的很多错误不是 token-level 格式错误，而是 trajectory-level preference：同样都能输出 JSON，哪个工具顺序、哪个关键字段、是否该拒绝，必须靠 reward 排序。

结果符合预期：project_robot 达到 1.0，browser_deferred 从 v2 的 0.2484 提到 0.7484，cross_source 从 0.6291 提到 0.8582。真正的收益来自 schema-aware reward：它不再只奖励“没有 forbidden tool”，而是检查 required tool coverage、critical fields、semantic fields、domain mixing 和 scope。缺点也很明确：safety_side_effect tool_acc 0.4429、coverage 0.4913，仍无法稳定处理 tau2 telecom 这类多步修复任务。corner case 是 gold 需要依次处理 airplane mode、network preference、VPN、data mode、data refuel 时，模型可能只调用 toggle_data 或 enable_roaming，形式安全但任务未完成。

8B tool-restraint GRPO：把“不该调用工具”显式训出来，但代价过大

tool-restraint 的设计目的，是修复 OOD quarantine 暴露的过度执行倾向：模型看到工具 schema 时，即使用户信息不足或任务存在风险，也倾向于生成某个执行工具。训练模式是在原 GRPO train 8,052 行上加入 1,200 行 generated restraint rows，形成 9,252 行 train mix；这些 rows 的特点是工具可见，但正确参考轨迹为空，奖励要求澄清/拒绝/不调用。

这个组合证明了一个重要负结论：只增强 no-tool 偏好会让模型过度保守。eval 中 project 仍为 1.0，browser 0.7323 也尚可，但 safety tool_acc 崩到 0.0311。解释是 safety suite 里很多任务不是“拒绝一切”，而是“先判断风险，再执行必要的安全修复序列”；8B tool-restraint 把 safety 过度简化成“少调用就是安全”。它的可用价值是作为 refusal/no-action 行为的对照模型和 reward sanity check，不适合作为主服务模型。

32B base eval：参数规模不能替代协议对齐

32B base eval 的设计目的，是检验一个直觉：更大的 Qwen3-VL base 是否天然更会 native tools。结果给出了反例：base_32b 在 sft_tool_call_holdout 上 tool_acc 0.3781，project 0.5923，browser 0.0419，cross 0.2379，甚至低于 base_8b 的部分指标。这说明项目工具能力不是单纯“模型越大越好”，而是高度依赖训练时是否见过本地 schema、native tools 模板和严格字段要求。

这个阶段的价值在于避免错误投资：如果不先做 base eval，后续 32B 训练失败时很难判断是 base 本身强、训练破坏了，还是 base 根本没适配。corner case 是 32B base 可以生成自然语言上合理的回答，但 native eval 不承认自然语言“我会去前台”这种响应，必须输出可执行 tool call；它在工具协议下的有效性远低于直觉预期。

32B SFT：最大、最稳的规模化收益来自监督协议对齐

32B SFT 的设计目的，是验证同一套 v2/tool-restraint 数据在更大模型上是否能带来更稳的 schema following。训练模式是 full language SFT + CPU offload，不引入 GRPO 的 rollout 和 reward 不确定性。这样设计的理由很朴素：32B 的容量更大，但如果 base 不懂项目 schema，第一步仍然应该是高质量监督对齐，而不是直接 RL。

结果显示 32B SFT 是很强的广谱 checkpoint：project 1.0，browser 0.7462，cross 0.8368，sft holdout 0.9542，safety 0.4083。它的收益是稳定、可复现、少 reward drift；缺点是 OOD quarantine 仍有 0.1998 forbidden_tool_rate，说明它学到了“按样例调用工具”，但拒绝/澄清的策略边界仍不够硬。可用性上，它适合作为 32B shadow baseline，尤其适合 project_robot、browser_deferred、cross_source 的观察流量；但 side-effect tools 仍应禁用或 mock。

32B GRPO ckpt100/200：RL 有安全收益，但 checkpoint selection 比步数更重要

32B GRPO 的设计目的，是在 32B SFT 已很强的基础上，看 online GRPO 能不能进一步改善安全和 OOD refusal。训练模式继续用 online GRPO gen=8，但工程成本显著上升：早期 gen=8/gen=4 跑不到第一步日志，后续 mbs3 能到约 step 259，遇到 parser bug；mbs4 restart 又碰到 ZeRO-3 CPU-offload/MACA memory handle 问题。

结果显示 GRPO 并非“越训越好”。ckpt100 在 OOD quarantine 上明显优于 ckpt200：execution_when_should_refuse 0.0400 vs 0.3340，forbidden 0.0389 vs 0.3330；但 D-suite 上，ckpt100 的 safety tool_acc 0.3875 低于 32B SFT 0.4083，cross 0.8270 也低于 SFT 0.8368。由此可见，32B GRPO 的价值主要在 OOD 安全抑制，而不是全面提升所有 deterministic suite。可用性上，ckpt100 是更保守的安全候选；ckpt200 因后期漂移，不应因为步数更多就默认优先。

收益归因公式：把提升拆成协议、奖励、规模和安全边界

为了避免把所有提升都笼统归因给“GRPO 有用”，可以把某个 suite 指标 \(M\) 的变化拆成四类增量：

\[ \Delta M = \Delta M_{\mathrm{protocol}} + \Delta M_{\mathrm{reward}} + \Delta M_{\mathrm{scale}} + \Delta M_{\mathrm{restraint}} + \epsilon \]

变量解释：\(\Delta M_{\mathrm{protocol}}\) 表示从旧 prompt/tool-call 格式切到 native tools 的收益；\(\Delta M_{\mathrm{reward}}\) 表示 schema-aware reward 和 online GRPO 的收益；\(\Delta M_{\mathrm{scale}}\) 表示 8B 到 32B 的参数规模与容量收益；\(\Delta M_{\mathrm{restraint}}\) 表示 no-tool/tool-restraint 数据带来的安全边界变化；\(\epsilon\) 是数据采样、评测抽样、训练随机性和未建模交互项。实现映射：本报告用 v1_lora_grpo、v2_full_grpo、v3_full_grpo_schemaaware、32B SFT、32B GRPO ckpt100/200 的 eval ladder 来近似分离这些项。

8B 收益分析

8B 的收益主要来自两个阶段。第一，SFT 把 tool-call holdout 从 base 的 0.6564 拉到 0.94+ 级别，这是协议学习收益。第二，schema-aware GRPO 把 project 从 0.9923 提到 1.0，并把 browser 从 0.2484 提到 0.7484、cross 从 0.6291 提到 0.8582，这是 reward 对关键字段、semantic fields 和 domain mixing 的校正收益。

最不符合期望的是 safety：v3 safety tool_acc 0.4429、coverage 0.4913，虽然 forbidden 为 0，但多步安全任务仍常漏步骤。例如 tau2 telecom 任务 gold 需要 5 步，模型可能只调用 enable_roaming 或 toggle_data 一步。这说明“避免副作用”和“完成必要修复序列”之间仍缺中间 credit assignment。

更细地看，8B v3 的价值在于把工具调用从“能调用”推进到“能按 schema 精确调用”。Project robot 中 robotId、instruction_en、origin_text、坐标/地图字段等被 schema-aware reward 约束后，模型不再只是输出某个导航工具，而是更能贴合 AceAgent 实际执行路径。Browser 的提升也不是因为模型真的理解网页，而是因为 reward/eval 强化了 deferred action 的工具名与 strict field；但 WebLINX 的 UID/target 本质上仍依赖页面 grounding，离真实 browser runner 还有距离。

因此 8B v3 的可用性边界是：项目机器人近域任务可以进入带保护的 shadow，浏览器任务只能做离线/deferred 验证，安全副作用工具必须关闭或 mock。它的主要缺点不是“格式不对”，而是策略级 corner cases：多故障安全任务漏步、OOD quarantine 过度执行、未知 schema 下偶发猜工具。这些缺点都指向下一步需要 step-level reward、hard negative replay 和真实环境 runner。

32B 收益分析

32B base 在 native tools 下反而弱，说明 Qwen3-VL 32B 的通用能力不能自动转化为本地 AceAgent schema 能力。32B SFT 后出现最大跳跃：sft tool_acc 0.3781 -> 0.9542，project 0.5923 -> 1.0，browser 0.0419 -> 0.7462，cross 0.2379 -> 0.8368。这个结果说明数据和协议对齐比参数规模本身更重要。

32B GRPO ckpt100/ckpt200 的 D-suite 差异很小，ckpt100 安全 tool_acc 0.3875、ckpt200 0.3737；cross ckpt100 0.8270、ckpt200 0.8280。OOD quarantine 上 ckpt100 明显优于 ckpt200：execution_when_should_refuse 0.0400 vs 0.3340，forbidden 0.0389 vs 0.3330。因此如果选 32B GRPO，应偏向 ckpt100，而不是“步数更多”的 ckpt200。

32B SFT 的核心价值是强监督吸收能力：同样的数据配方，32B 能更稳定地记住工具 schema、参数结构和跨源工具分布，而且不引入 reward drift。它的缺点也来自 SFT 本身：如果训练集中有大量“用户要求 -> 工具执行”的模式，模型会倾向把风险任务也解释成可执行任务。换句话说，32B SFT 更像一个强大的 schema follower，而不是足够保守的 policy reasoner。

32B GRPO ckpt100 则更像一个安全倾向修正器。它牺牲了一点 D-suite deterministic coverage，换来了 OOD quarantine 上显著更低的 forbidden/execution 率。这在真实业务中有明确价值：如果错误执行的代价高于漏执行，ckpt100 比 32B SFT 更值得作为 shadow 候选；如果业务更看重任务完成率，且外部有可靠安全 gate，32B SFT 反而更稳。ckpt200 的教训是，RL checkpoint selection 不能只看训练步数和 cross 平均分，必须把 OOD refusal、安全漂移作为一等指标。

风险与后续建议

  1. 安全多步 coverage 是当前 gate。forbidden 低不等于安全，因为模型可能漏掉必要修复步骤或在 OOD 中直接执行。
  2. Browser UID/target 不允许语义放宽。浏览器 suite 的 target/uid 必须 strict，否则看起来 semantic_match 好，实际会点错页面元素。
  3. Reward 需要从轨迹级走向步骤级。当前 schema-aware reward 已解决字段级问题，但 tau2 多步任务需要每步 credit assignment，否则容易一两步拿部分分。
  4. Tool-restraint 要重新配平。下一版可把 no-tool rows 与“必须调用才能安全完成”的正样例成对采样，避免 8B restraint 过度保守。
  5. 保持 schema 自动同步。所有训练/eval 应从 server/tools/registry.py 导出 schema，避免 instruction/destination/instruction_en 这类历史字段漂移。
  6. 真实 shadow 必须记录状态后果。当前 deterministic eval 主要评工具调用；真实系统还要记录 tool result、取消、超时、机器人 mutex、地图匹配失败和用户中断。
