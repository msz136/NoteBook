具身智能项目数据处理体系报告

基于 pryer 项目实际代码与工程实践的深度分析 | 2026-05-22

问题（Question）

在一个涉及 VLA（Vision-Language-Action）模型训练、强化学习基础设施、多模态感知与机器人部署的大型具身智能项目中，数据处理体系是如何设计与实现的？其核心思想、方法论、工程架构、数据来源与落地场景是什么？

背景与动机（Background & Motivation）

本报告基于 pryer 项目——一个包含 20+ 子项目线的具身智能研究平台快照。该项目的核心目标是构建统一的机器人 VLA 模型，将视觉理解、语言指令和动作执行融合在一个序列建模框架中。

在这一目标下，数据处理不是外围辅助工作，而是系统的核心基础设施。原因在于：

  • 多源异构：数据来自人体遥操作（ACE 手部关键点）、机器人传感器（Zarr/H5 格式）、公开数据集（DROID、OXE）、仿真环境（LIBERO）等，格式各异
  • 时间对齐要求极高：VLA 模型需要观测（图像）与动作（关节角）在时间轴上精确对齐，任何偏差都会导致训练信号错误
  • 规模化需求：数万条 episode、数百万帧数据需要高效并行处理
  • 统一表示：不同来源的数据必须转换为统一格式才能混合训练

设计思想：数据即训练信号的正确性保证

项目的数据处理哲学可以概括为三个核心原则：

  1. 时间戳是第一公民：观测-动作对的时间对齐精度直接决定模型学到的因果关系是否正确。项目为此设计了 PTS 反写机制（详见后文）。
  2. 格式统一优先于性能优化：所有异构数据源必须先转换为 LeRobot V3.0 格式，再进入训练流水线。这牺牲了一些灵活性，但换来了混合训练的可组合性。
  3. 逆运动学在数据侧完成：人体演示数据的 IK 计算在数据转换阶段完成（而非训练时在线计算），确保训练时的数据读取是纯 I/O 操作，不引入计算瓶颈。

核心管线一：ACE 人体演示 → LeRobot

设计目标

将人类操作员通过 ACE 系统采集的手部关键点数据，转换为机器人可执行的关节角度序列。这是一个从"人体空间"到"机器人空间"的映射问题。

处理流程

Parquet (手部21关键点×3D + 状态) │ ▼ bilateral_hand_state_from_keypoints() → 双臂末端执行器位姿 (ee_pos[6], ee_rot[6]) → 归一化夹爪宽度 (gripper_norm[2]) │ ▼ DualArmCamEeIk.ee_cam_to_joints() → Pinocchio IK 求解 → 12-DOF 关节角 (joints[12]) → 夹爪宽度 (gripper_w[2]) │ ▼ LeRobot V3.0 Dataset ├── videos/: 3视角 (global 512×512, left/right wrist 480×848) ├── data/: state.* + action.* (Parquet) └── meta/: info.json + episodes/

设计亮点

  • 种子前向传播：forward_hand_seeds_for_episode 在处理 episode 前先扫描全部帧，为 IK 求解器提供全局一致的初始猜测，避免关节角跳变
  • 状态连续性：q_prev_left/right 将上一帧的 IK 解作为下一帧的初始值，保证关节轨迹平滑
  • Action = State：action.joints = joints.copy()，与 Agilex 转换保持一致——当前帧的状态即为当前帧的动作标签
  • FPS=3：人体演示采样率为 3Hz，远低于机器人控制频率，适合 VLA 模型的粗粒度动作预测

核心管线三：数据集尾部截断与 PTS 时间戳精确对齐

问题背景

机器人演示数据的末尾通常包含"无效尾巴"——操作员完成任务后的静止或随意动作。这些帧会引入噪声训练信号。简单地截断 Parquet 数据是不够的，因为视频文件的帧时间戳（PTS）在重新编码后会发生漂移，导致数据表中的 timestamp 列与视频帧不再对齐。

核心挑战：LeRobot 在查询视频帧时计算 query_ts = from_timestamp + data_timestamp。如果 data_timestamp 与视频中的实际 PTS 不匹配，就会读取到错误的帧，导致观测-动作对错位。

三阶段处理流水线

Phase 1：GPU 加速视频裁剪 + ffprobe PTS 探测

# 自动探测可用的硬件编码器
HW_ENCODERS = [
    "h264_videotoolbox",   # macOS Apple Silicon / Intel
    "h264_nvenc",          # NVIDIA GPU (CUDA)
    "h264_vaapi",          # Linux VA-API (Intel/AMD)
    "h264_qsv",            # Intel Quick Sync Video
]

def detect_hw_encoder() -> str:
    """逐个测试硬件编码器可用性，全部失败回退到 libx264"""
    for enc in HW_ENCODERS:
        if enc not in available:
            continue
        # 实际编码 1 帧测试
        test_cmd = ["ffmpeg", "-f", "lavfi", "-i", "nullsrc=s=64x64:d=0.1:r=30",
                    "-frames:v", "1", "-c:v", enc, "-f", "null", "-"]
        r = subprocess.run(test_cmd, capture_output=True, timeout=15)
        if r.returncode == 0:
            return enc
    return "libx264"  # 软件回退
# 视频裁剪：精确到帧的 output seeking
cmd = ["ffmpeg", "-i", input_path]
cmd.extend(["-ss", f"{start:.6f}"])          # 精确起始时间
cmd.extend(["-t", f"{duration:.6f}"])        # 精确持续时间
cmd.extend(["-c:v", encoder])                # GPU 编码器
cmd.extend(["-g", "2"])                      # GOP=2，密集关键帧
cmd.extend(["-r", str(fps)])                 # 恒定帧率
cmd.extend(["-video_track_timescale", str(fps * 10000)])  # 高精度时间基
# 从编码后的视频中提取每帧的实际 PTS
def probe_video_timestamps(video_path: str, fps: int) -> list[float]:
    """用 ffprobe 读取 MP4 容器中每个视频 packet 的 pts_time"""
    cmd = ["ffprobe", "-v", "error", "-select_streams", "v:0",
           "-show_entries", "packet=pts_time", "-of", "csv=p=0",
           video_path]
    r = subprocess.run(cmd, capture_output=True, text=True, timeout=600)
    timestamps = [float(line) for line in r.stdout.strip().split("\n")
                  if line.strip() and line.strip() != "N/A"]
    timestamps.sort()  # packet 顺序可能是解码序(DTS)，排序得到呈现序(PTS)
    return timestamps

设计亮点

  • PTS 反写机制：这是整个数据处理体系中最精巧的设计。不是假设视频帧均匀分布，而是从实际编码结果中提取真实时间戳，反向写入数据表，从根本上消除时间对齐误差
  • 跨平台 GPU 加速：自动探测 VideoToolbox/NVENC/VAAPI/QSV，在 macOS/Linux/Windows 上都能利用硬件加速
  • 多 episode 视频文件处理��一个 MP4 文件可能包含多个 episode 的视频流，工具正确处理分段裁剪 + concat 拼接
  • 验证闭环：内置 verify_trimmed_dataset() 函数，用 LeRobotDataset API 加载裁剪后的数据集验证完整性

设计思想

def create_xe_data_loader(data_config, ...):
    # 1. 解析组名 → 路径列表
    repo_groups = data_config.repo_group.split(",")
    all_paths = []
    for group_name in repo_groups:
        paths = getattr(data_constant, group_name)
        all_paths.extend(paths)

    # 2. 加载每个路径为 LeRobotDataset
    datasets = []
    for path in all_paths:
        ds = LeRobotDataset(path, delta_timestamps=action_chunk_config)
        ds = AlignDataset(ds)      # 坐标对齐
        ds = FilterDataset(ds)     # 过滤无效帧
        datasets.append(ds)

    # 3. 合并为 ConcatDatasetWithMeta
    concat_ds = ConcatDatasetWithMeta(datasets)

    # 4. 创建分布式 DataLoader
    sampler = DistributedSampler(concat_ds, ...)
    return DataLoader(concat_ds, sampler=sampler, ...)

        elif self.robot_type == "Franka":
            ...

        # 统一图像尺寸

为什么选择 LeRobot 格式

  • 视频压缩：图像序列存储为 MP4 视频而非逐帧 PNG/JPEG，存储效率提升 10-50 倍
  • Chunk 分片：大数据集自动分片（video_files_size_in_mb=8），支持并行读取
  • HuggingFace 生态兼容：可直接上传到 HuggingFace Hub 共享
  • Delta Timestamps：支持 action chunking（一次预测未来 N 步动作）的时间偏移查询
  • 统计信息内置：stats.json 提供归一化所需的统计量，无需额外扫描

关键设计决策分析

决策 1：为什么 Action = State（同帧）？

在 ACE 转换中，action.joints = joints.copy()——当前帧的动作标签就是当前帧的状态。这看似冗余，但与 VLA 模型的 action chunking 机制配合：模型预测的是"从当前帧开始的未来 N 步动作序列"，通过 delta_timestamps 在 DataLoader 中自动构建。

决策 2：为什么 FPS 差异如此大？

  • ACE 人体演示：3 Hz（人体动作缓慢，高频采样冗余）
  • CobotMagic 触觉：30 Hz（触觉信号变化快，需要高频采样）
  • 训练时通过 frame_interval 统一到目标频率

决策 3：为什么需要 GPU 视频编码？

Trim 工具处理的数据量巨大（数万 episode × 多视角视频）。CPU 软编码是瓶颈：

  • NVENC (NVIDIA)：比 libx264 快 5-10 倍
  • VideoToolbox (Apple)：M 系列芯片的硬件编码器
  • 自动探测 + 回退机制确保跨平台可用性
