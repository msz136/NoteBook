成功率（Success Rate, SR）的定义如下，令 \(s_i\) 表示第 \(i\) 个任务成功次数，\(n_i\) 表示第 \(i\) 个任务总 trial 数：

\[ \mathrm{SR}=\frac{\sum_{i=1}^{N} s_i}{\sum_{i=1}^{N} n_i} =\frac{297}{480}=0.61875. \]

变量解释：\(N=24\) 是 kitchen task 数；每个任务 \(n_i=20\)，所以总 trial 数为 \(480\)。实现映射：该式对应本地 summary.json 中的 overall_successes、overall_trials 与 overall_success_rate 字段。

基础知识栈

RoboCasa 与 Kitchen24

RoboCasa 是面向厨房场景的机器人仿真框架，构建在 robosuite / MuJoCo 生态上，提供多样化厨房布局、物体、家具和机器人操作任务。原论文报告了 100 个任务、120 个场景、2500+ 3D 物体与 100K+ 合成轨迹规模，用来研究大规模 imitation learning（模仿学习）和 generalist robots（通用机器人）。

本地 kitchen24 是 Cosmos/RoboCasa policy recipe 中常用的 24 个厨房原子操作任务集合，包括 pick-and-place、开关门/抽屉、水龙头/炉灶/微波炉、咖啡机相关操作等。它的难点不只是视觉识别，还包括接触丰富（contact-rich）的末端执行器控制、长 horizon、物体遮挡、不同布局和实例 split。

VLA、π0.5 与动作分块

视觉语言动作模型（Vision-Language-Action Model, VLA）把图像、机器人状态和语言指令联合编码，然后直接输出机器人动作。π0.5 是 OpenPI 体系中用于开放世界泛化的 VLA base model，OpenPI 官方说明其 base checkpoints 经过 10k+ 小时机器人数据预训练，可用于 fine-tuning。

动作分块（Action Chunking）表示模型不是每个控制步只预测一个动作，而是一次输出 \(H\) 个未来动作：

\[ A_{t:t+H-1} = \{a_t, a_{t+1}, \ldots, a_{t+H-1}\}, \quad a_t \in \mathbb{R}^{d_a}. \]

变量解释：\(H\) 是 action horizon（动作预测长度），本地 pi05_robocasa 配置为 10；\(d_a\) 是内部动作维度，π0.5 内部常用 32，RoboCasa Panda 任务实际控制只取前 7 维。实现映射：Pi0Config(action_horizon=10) 与 RobocasaOutputs(action_dim=7) 共同决定“预测 10 步、执行 7D 动作”。

闭环控制与 Online Rollout

离线 loss 只衡量模型在数据集样本上预测动作的误差；online rollout（在线闭环展开）会把预测动作真正送入仿真环境，环境状态再反过来影响下一次观测。这个闭环会放大小的动作偏差、相机预处理偏差和 normalization 错误，因此“loss 降得漂亮”不等于 “success rate 一定高”。

本地 Qwen+Cosmos 分支就是典型例子：action/future-frame loss 下降到很低，但 kitchen24 闭环 SR 只有 0% 到约 40%，说明模型可能学到了离线分布上的目标，却没有形成稳定的控制接口。

7D RoboCasa Action → 32D π0.5 Action Space 的具体机理

这一步不是简单为了“凑 shape”，而是为了让 RoboCasa 的 7D Panda action 复用 π0.5 base 已经预训练好的 32D action expert。换句话说，本地项目没有把模型动作头改成 7D，而是把 RoboCasa 数据嵌入到 π0.5 原生的 32D 动作坐标系里，然后在输出侧再投影回环境可执行的 7D。

令 \(a_t^{env}\in\mathbb{R}^{7}\) 表示 RoboCasa 环境动作（environment action），\(D=32\) 表示 π0.5 内部动作维度（internal action dimension），定义嵌入矩阵（embedding matrix）\(P\in\mathbb{R}^{32\times7}\)：

\[ P = \begin{bmatrix} I_7 \\ 0_{25\times7} \end{bmatrix}, \qquad a_t^{32}=P a_t^{env}. \]

变量解释：\(I_7\) 是 7 维单位矩阵，\(0_{25\times7}\) 是零矩阵；\(P\) 把真实 7D action 放在 32D 向量的前 7 维，后 25 维是 padding 子空间。实现映射：归档配置直接调用 PadStatesAndActions(model_config.action_dim)；同源 OpenPI 快照中该 transform 对 state 和 actions 的最后一维执行 pad_to_dim(..., model_action_dim)。

对一个长度为 \(H=10\) 的 action chunk，这个嵌入逐时间步应用：

\[ A^{32}_{t:t+H-1} = A^{env}_{t:t+H-1} P^\top \in \mathbb{R}^{H\times32}, \quad A^{env}_{t:t+H-1}\in\mathbb{R}^{H\times7}. \]

这里 \(A^{env}\) 是 LeRobot loader 从 actions 字段构造出的 RoboCasa action sequence；\(A^{32}\) 是进入 π0.5 flow matching action expert 的训练 target。实现上不一定显式构造 \(P\)，而是用 padding 函数完成同样的线性嵌入。

输出侧对应一个选择矩阵（selection matrix）\(S\in\mathbb{R}^{7\times32}\)：

\[ S = \begin{bmatrix} I_7 & 0_{7\times25} \end{bmatrix}, \qquad \hat{a}_t^{env}=S\hat{a}_t^{32}. \]

变量解释：\(S\) 只取模型输出 32D action 的前 7 维。实现映射：归档配置中 RobocasaOutputs(action_dim=7) 是直接证据；同源 policy 输出类的注释写明“因为训练前 padded 到模型动作维度，所以 inference 只返回前 N 维”。RoboCasa 本地版本的完整 RobocasaOutputs 未归档，因此具体代码行以配置调用和同源 policy 作为证据边界。

训练时的 flow matching 不是在 7D 空间里训练一个新头，而是在 32D 空间中构造 noisy action：

\[ x_t=\tau\epsilon + (1-\tau)a^{32}, \qquad u_t=\epsilon-a^{32}, \qquad v_\theta=f_\theta(o,s,c,x_t,\tau)\in\mathbb{R}^{32}. \]

变量解释：\(\tau\in[0,1]\) 是 flow matching 时间，\(\epsilon\sim\mathcal{N}(0,I_{32})\)，\(o\) 是图像观测，\(s\) 是 state，\(c\) 是 prompt，\(v_\theta\) 是 action expert 预测的 32D velocity。实现映射：PaliGemma+Cosmos 源码中可见 x_t = time * noise + (1 - time) * actions、u_t = noise - actions、action_out_proj(...) 输出 32D；普通 π0.5 主线采用同类 action expert 机制。

普通 pi05_robocasa 配置没有显式设置 action_loss_dim=7，因此按归档证据应理解为在 32D padded target 上训练。由于后 25 维 target 是 padding 常量，模型被约束在 padding 子空间输出接近 padding 值；真正被 RoboCasa 执行的仍只有前 7 维：

\[ \mathcal{L}_{32D} = \frac{1}{BH32} \sum_{b,h,j\le32} \left(v_{\theta,b,h,j}-u_{b,h,j}\right)^2, \qquad a^{exec}_{b,h}=S\,\mathrm{denorm}\!\left(\hat{a}^{32}_{b,h}\right). \]

这条公式解释了为什么“输出头不改成 7D”仍能执行：训练/采样保持 32D，以兼容 π0.5 base；eval 前输出 transform 只截取前 7D。对 Cosmos 探索分支，配置里出现 action_loss_dim=7，源码中有 action_loss = action_loss[..., :action_loss_dim]，因此那些分支会只对前 7 维计算 action loss；这是与最终普通主线不同的头部/目标边界。

def adapt_robocasa_action_for_pi05(action_7d, *, horizon=10, model_action_dim=32):
    # action_7d: shape (H, 7), already delta action from RoboCasa.
    # Evidence: LeRobotRobocasaDataConfig states RoboCasa actions are already delta,
    # so extra_delta_transform=False avoids a second delta conversion.
    action_7d = action_7d[:horizon]

    # Build the 32D pi0.5 target. This is equivalent to multiplying by P^T:
    # A_32 = [A_7, padding]. In same-source OpenPI transforms this is done by
    # PadStatesAndActions(model_action_dim) / pad_to_dim(..., axis=-1).
    action_32d = zeros(shape=(horizon, model_action_dim))
    action_32d[:, :7] = action_7d

    # The padded dimensions are not sent to the robot. They exist so the action
    # expert keeps the pi0.5 base interface and can reuse 32D pretrained weights.
    return action_32d


def parse_pi05_output_for_robocasa(pred_action_32d, norm_stats):
    # pred_action_32d: model output chunk in normalized 32D action space.
    # First undo action normalization using assets/norm_stats.
    denorm_action_32d = unnormalize(pred_action_32d, norm_stats)

    # RobocasaOutputs(action_dim=7) implements the selection matrix S:
    # keep only the first seven executable Panda/RoboCasa control dimensions.
    env_action_chunk = denorm_action_32d[:, :7]

    # The online rollout client executes this 7D chunk for a few steps, then
    # asks the policy server to replan. Final eval uses replan_steps=5.
    return env_action_chunk

训练目标、Loss 与数学表达

π0.5 Flow Matching 动作目标

π0.5 的连续动作头可用 flow matching（流匹配）理解。令 \(a\) 表示数据集中的目标动作 chunk，\(\epsilon \sim \mathcal{N}(0,I)\) 表示高斯噪声，\(t \in [0,1]\) 表示噪声时间：

\[ x_t = t\epsilon + (1-t)a,\qquad u_t = \epsilon - a. \]

变量解释：\(x_t\) 是在真实动作 \(a\) 与噪声 \(\epsilon\) 之间插值得到的 noisy action；\(u_t\) 是模型应学习的速度场（velocity field）。实现映射：本地 PaliGemma+Cosmos 源码中出现 x_t = t * noise + (1 - t) * actions 与 u_t = noise - actions，普通 π0.5 action expert 采用同类目标。

动作 loss 是模型预测速度 \(v_\theta(x_t, o, c, t)\) 与目标速度 \(u_t\) 的均方误差：

\[ \mathcal{L}_{action} = \frac{1}{BHD_a} \sum_{b=1}^{B}\sum_{h=1}^{H}\sum_{j=1}^{D_a} \left\| v_\theta(x_{t,b,h,j}, o_b, c_b, t_b) - u_{t,b,h,j} \right\|_2^2. \]

变量解释：\(B\) 是 batch size，本地通常为 256；\(H=10\) 是 action horizon；\(D_a=32\) 是内部动作维度，或在 action_loss_dim 打开时只计算前若干维。实现映射：训练脚本记录 action_expert_loss，Cosmos 分支源码中若 action_loss_dim 非空，会对 loss 的最后一维切片。

Cosmos 分支总 Loss

当启用 world-model backbone 时，总目标增加未来帧 latent 监督：

\[ \mathcal{L}_{total} = \mathcal{L}_{action} + \lambda_{video}\mathcal{L}_{future}, \qquad \mathcal{L}_{future} = \mathrm{MSE}\left(z^{pred}_{t+1:t+K}, z^{target}_{t+1:t+K}\right). \]

变量解释：\(\lambda_{video}\) 是 cosmos_video_loss_weight；\(z^{pred}\) 和 \(z^{target}\) 是 Cosmos video expert 的预测/目标未来帧 latent；\(K=4\) 对应 cosmos_num_future_frames=4。实现映射：PaliGemma+Cosmos 源码把 future_frame_loss 加到 total_loss；Qwen+Cosmos 日志同时输出 loss、action_expert_loss 与 future_frame_loss。

离线 Loss 与闭环 SR 的关系

离线动作 MSE 可写作数据分布上的期望：

\[ \mathbb{E}_{(o,c,a)\sim \mathcal{D}_{train}} \left[ \mathcal{L}_{action}(o,c,a) \right], \]

而 online rollout 的成功率来自模型诱导出的状态分布 \(\mathcal{D}_{\pi_\theta}\)：

\[ \mathrm{SR}(\pi_\theta) = \mathbb{E}_{\tau \sim p(\tau \mid \pi_\theta, \mathcal{E})} \left[ \mathbf{1}\{\tau \text{ satisfies task success predicate}\} \right]. \]

变量解释：\(\mathcal{D}_{train}\) 是离线示教数据分布；\(\mathcal{D}_{\pi_\theta}\) 是模型在环境中自己执行后产生的状态分布；\(\tau\) 是一条 rollout 轨迹。实现映射：Qwen+Cosmos loss 低但 SR 低，说明离线目标与闭环任务成功之间存在 distribution shift（分布偏移）、动作接口或视觉/状态适配问题。

def training_step(batch, model, optimizer):
    # 1. Read normalized observation and padded action chunks.
    observation = Observation.from_dict(batch)
    actions = batch["actions"]  # Shape: batch, horizon, 32

    # 2. Sample flow-matching noise and interpolation time.
    noise = sample_normal_like(actions)
    t = sample_uniform(batch_size=actions.shape[0])
    x_t = t * noise + (1 - t) * actions
    target_velocity = noise - actions

    # 3. Predict action velocity conditioned on image, state and prompt.
    pred_velocity = model.denoise_step(observation, x_t, t)
    action_loss = mse(pred_velocity, target_velocity)

    # 4. Cosmos branches optionally add future-frame supervision.
    if model.use_wm_backbone:
        future_loss = model.cosmos_video_loss(observation)
        total_loss = action_loss + model.cosmos_video_loss_weight * future_loss
    else:
        total_loss = action_loss

    # 5. Backpropagation and checkpoint/logging follow train_pytorch_qwen.py.
    total_loss.backward()
    optimizer.step()
    optimizer.zero_grad()
    return total_loss

def evaluate_kitchen24(tasks, trials_per_task, policy_client, env_factory):
    # Each task is evaluated independently so per-task success rates can be reported.
    results = {}
    for task_name in tasks:
        successes = 0
        for trial_id in range(trials_per_task):
            env = env_factory(task_name, seed=7, deterministic=True)
            obs = env.reset()
            action_chunk = None
            chunk_index = 0

            for step in range(500):
                # Replan every fixed number of simulator steps.
                if step % 5 == 0 or action_chunk is None:
                    response = policy_client.infer(obs)
                    action_chunk = response["actions"]  # Shape: horizon, 7
                    chunk_index = 0

                # Execute one 7D Panda action and read the next observation.
                action = action_chunk[chunk_index]
                obs, reward, done, info = env.step(action)
                chunk_index += 1

                # RoboCasa task success predicate decides whether the episode succeeded.
                if info.get("success", False) or done:
                    successes += int(info.get("success", False))
                    break

        results[task_name] = successes / trials_per_task
    return results

跨 Run 差分视角（Delta View）

为了回答“每一次 run 相较上一 run 到底改了什么”，本报告把第 \(r\) 次实验抽象成一个系统状态 \(S_r\)。这个状态不是单个 checkpoint，而是数据格式、模型结构、输入输出头、训练目标和评估闭环的组合：

\[ S_r = \left(D_r, M_r, H_r, \mathcal{L}_r, E_r, Y_r\right) \]

变量解释：\(D_r\) 是数据与 schema（data and schema），\(M_r\) 是 backbone / world model / action expert 等模型结构（model architecture），\(H_r\) 是输入头和输出头（input and output heads），\(\mathcal{L}_r\) 是训练目标（loss objective），\(E_r\) 是 online rollout 评估设置（evaluation harness），\(Y_r\) 是结果与失败模式（outcome）。实现映射：这些量分别对应 config.py、模型源码、transform、训练日志和 results.txt/summary.json。

两个相邻 run 的真正差异可以写成：

\[ \Delta S_r = S_r \ominus S_{r-1} = \left(\Delta D_r, \Delta M_r, \Delta H_r, \Delta \mathcal{L}_r, \Delta E_r, \Delta Y_r\right) \]

这里的 \(\ominus\) 不是普通减法，而是结构化 diff：例如从 PaliGemma 换到 Qwen 属于 \(\Delta M_r\)，把 7D RoboCasa action padding 到 32D 属于 \(\Delta H_r\)，把 action-only loss 改成 action + future-frame loss 属于 \(\Delta \mathcal{L}_r\)。

成功率（success rate, SR）在一个任务集合 \(\mathcal{T}\) 上定义为：

\[ \mathrm{SR}(S_r;\mathcal{T}) = \frac{\sum_{\tau \in \mathcal{R}(S_r,\mathcal{T})}\mathbf{1}[\tau \text{ success}]}{|\mathcal{R}(S_r,\mathcal{T})|} \]

变量解释：\(\mathcal{R}(S_r,\mathcal{T})\) 表示用第 \(r\) 个系统状态在任务集合 \(\mathcal{T}\) 上跑出的 rollout 集合，\(\mathbf{1}[\tau \text{ success}]\) 是 episode 是否成功的指示函数。实现映射：本地最终 run 中 \(|\mathcal{R}|=24\times20=480\)，成功 episode 数为 297，因此 \(\mathrm{SR}=297/480=0.61875\)。

当两个 run 的任务覆盖不完全一致时，本报告只把 \(\Delta \mathrm{SR}\) 当作上下文信号；只有评估任务、trial 数、replan 和 split 基本一致时，才把它当作强对比：

\[ \Delta \mathrm{SR}_r = \mathrm{SR}(S_r;\mathcal{T}_r) - \mathrm{SR}(S_{r-1};\mathcal{T}_{r-1}) \quad \text{with comparability flag } \gamma_{r,r-1} \]

\(\gamma_{r,r-1}=1\) 表示两个 run 的评估口径可比；\(\gamma_{r,r-1}=0\) 表示只能做方向性分析。例如 Run 5 对 Run 4 是同为 24 tasks、20 trials/task 的强对比；Run 3 对 Run 2 因任务覆盖不同，只能说明 Qwen+Cosmos 早期闭环失败，而不能作为严格 benchmark 差值。

def compare_adjacent_runs(prev, curr):
    # 1. Treat each run as a structured system state, not just a checkpoint path.
    #    This prevents mixing data schema changes with model architecture changes.
    delta = {
        "data": diff(prev.data_schema, curr.data_schema),
        "model": diff(prev.model_arch, curr.model_arch),
        "heads": diff(prev.io_heads, curr.io_heads),
        "loss": diff(prev.loss_objective, curr.loss_objective),
        "eval": diff(prev.eval_harness, curr.eval_harness),
    }

    # 2. Decide whether the success-rate delta is a strict comparison.
    #    Same task set, same trials per task, same split and similar rollout setup
    #    are required before we interpret delta_sr as benchmark evidence.
    comparable = (
        prev.task_set == curr.task_set
        and prev.num_tasks == curr.num_tasks
        and prev.trials_per_task == curr.trials_per_task
        and prev.replan_steps == curr.replan_steps
    )

    # 3. Compute the metric delta, but attach the comparability flag.
    delta_sr = curr.success_rate - prev.success_rate

    # 4. Explain the run by connecting design deltas to observed failures or gains.
    #    In this report, a gain is not credited to a parameter unless it changes
    #    data semantics, model behavior, training objective, or rollout behavior.
    return {
        "delta": delta,
        "delta_sr": delta_sr,
        "comparable": comparable,
        "interpretation": analyze_failure_modes(prev, curr, delta),
    }

\[ \Delta S_2 = \left( +D_{\mathrm{LeRobot\ RoboCasa}}, M_{\mathrm{PaliGemma\ unchanged}}, +H_{\mathrm{7D\ to\ 32D}}, +\mathcal{L}_{\mathrm{flow\ action}}, E_{\mathrm{same\ closed\ loop}} \right) \]

实现映射：\(D_{\mathrm{LeRobot\ RoboCasa}}\) 对应 LeRobotRobocasaDataConfig；\(H_{\mathrm{7D\ to\ 32D}}\) 对应 PadStatesAndActions(model_config.action_dim) 与 RobocasaOutputs(action_dim=7)；\(\mathcal{L}_{\mathrm{flow\ action}}\) 对应 π0.5 action expert 的 flow matching 训练目标。

7D RoboCasa action 到 32D π0.5 内部动作空间的适配，不是改模型输出层为 7D，而是定义从环境动作空间到 π0.5 内部动作空间的嵌入 \(P\)，并在输出侧用选择矩阵 \(S\) 截回可执行维度：

\[ P = \begin{bmatrix} I_7\\ 0_{25\times7} \end{bmatrix}, \quad S= \begin{bmatrix} I_7 & 0_{7\times25} \end{bmatrix}, \quad A^{32}_{t:t+H-1} = A^{env}_{t:t+H-1}P^\top, \quad \hat{A}^{env}_{t:t+H-1}=S\hat{A}^{32}_{t:t+H-1}. \]

变量解释：\(A^{env}\in\mathbb{R}^{H\times7}\) 是 RoboCasa/Panda 控制器使用的动作 chunk，\(A^{32}\in\mathbb{R}^{H\times32}\) 是 π0.5 action expert 内部动作 chunk，\(H=10\) 来自 action_horizon=10。实现映射：PadStatesAndActions(model_config.action_dim) 实现 \(P\) 的效果；RobocasaOutputs(action_dim=7) 实现 \(S\) 的效果。

在 flow matching 训练中，动作 expert 仍然学习 32D velocity field；普通 pi05_robocasa 主线没有显式 action_loss_dim=7，因此 padded 维度也参与保持 32D 接口稳定：

\[ x_\tau=\tau\epsilon+(1-\tau)A^{32}, \quad u_\tau=\epsilon-A^{32}, \quad \mathcal{L}_{Run2} = \frac{1}{BH32} \sum_{b,h,j} \left(v_{\theta,b,h,j}-u_{\tau,b,h,j}\right)^2. \]

变量解释：\(x_\tau\) 是 noisy 32D action，\(u_\tau\) 是目标 velocity，\(v_\theta\) 是 action expert 输出。实现映射：Cosmos 源码中能直接看到 x_t、u_t、action_out_proj；普通 π0.5 主线用同一类 action expert 目标。与之相对，Qwen/PaliGemma+Cosmos 探索配置显式设置 action_loss_dim=7，会只计算前 7 维 action loss。

def run2_repack_and_pad(lerobot_sample, model_config):
    # 1. Repack dataset keys into the observation namespace expected by OpenPI.
    #    This is the data-side bridge from RoboCasa LeRobot format to pi0.5 format.
    obs = {
        "observation/image": lerobot_sample["image"],
        "observation/secondary_image": lerobot_sample["secondary_image"],
        "observation/wrist_image": lerobot_sample["wrist_image"],
        "observation/state": lerobot_sample["state"],   # 9D proprioceptive state
        "prompt": lerobot_sample["prompt"],             # task-derived language command
    }

    # 2. RoboCasa actions are already delta actions, so no extra DeltaActions transform.
    #    This avoids applying a second delta conversion that would distort control scale.
    action_7d = lerobot_sample["actions"]

    # 3. Apply the embedding matrix P without explicitly materializing it:
    #    A_32 = [A_7, 0, ..., 0]. In luoshuang's archived config this is wired
    #    through PadStatesAndActions(model_config.action_dim); same-source OpenPI
    #    shows it pads the final dimension of both state and actions.
    action_32d = zeros(shape=(model_config.action_horizon, model_config.action_dim))
    action_32d[:, :7] = action_7d[:model_config.action_horizon]

    # 4. Train the action expert in the 32D pi0.5 action space.
    #    This keeps the base model's action_in/action_out interface unchanged.
    #    For the final pi05_robocasa config, no explicit action_loss_dim=7 is
    #    archived, so the padded 32D target is the conservative interpretation.
    train_target = action_32d

    # 5. At serving time, RobocasaOutputs(action_dim=7) applies the selection
    #    matrix S: denormalize the 32D chunk and return only the first 7 dims.
    return obs, train_target

def run3_train_with_qwen_cosmos(batch, model, optimizer, lambda_video):
    # 1. Build the same RoboCasa action target as Run 2.
    #    This preserves the 7D-to-32D action supervision contract.
    action_32d = pad_7d_actions_to_32d(batch["actions"])

    # 2. Add future image sequence supervision for Cosmos.
    #    The current main camera image is now both policy input and video target source.
    future_frames = batch["future_images"]["image"]

    # 3. Encode image and language with Qwen instead of PaliGemma.
    #    This is a large architecture delta because tokenization and visual features change.
    qwen_prefix = model.qwen_vl.encode(batch["images"], batch["prompt"])

    # 4. Compute action flow-matching loss.
    #    The action expert must predict the velocity from noisy action x_t to clean action a.
    action_loss = model.action_expert_loss(qwen_prefix, batch["state"], action_32d)

    # 5. Compute future-frame loss and optionally feed video context into the policy.
    #    This adds a second objective that may help dynamics but may also compete with control.
    future_frame_loss, video_context = model.cosmos_loss(future_frames, batch["prompt"])

    # 6. Joint objective used for backpropagation.
    total_loss = action_loss + lambda_video * future_frame_loss
    total_loss.backward()
    optimizer.step()
    optimizer.zero_grad()
    return {"total_loss": total_loss, "action_loss": action_loss, "future_frame_loss": future_frame_loss}

            successes += int(result.success)
            total += 1

    # 4. Persist summary.json so the result is auditable.
    #    This is the evidence source for 297/480 = 0.61875.
    summary_writer.write(successes=successes, total=total, success_rate=successes / total)

成功原因分析。Run 5 的有效性来自“减少不必要的表征迁移”。PaliGemma/action expert 和 π0.5 base checkpoint 原生同源，RoboCasa 只需解决数据键名、图像方向、state/action padding 和 7D 输出截取。与 Run 4 相比，Run 5 去掉了 Qwen tokenizer 迁移、Cosmos future-frame 目标、视频上下文注入和多目标 loss 权衡，因此闭环控制更稳定。它并没有证明 world model 无用，而是证明在当前本地证据下，action-only 主线更符合已有 base prior。

目标与设计动机

这是后续更合理的 Cosmos 探索线：不再用 Qwen 替换掉 PaliGemma 主线，而是在 PaliGemma π0.5 的对齐基础上加入 Cosmos Predict2.5 world-model branch。设计动机是保留 pi05_base 的 PaliGemma/action expert 接口优势，同时让 Cosmos 提供未来帧 representation。

相较上一 Run 的改造：Run 5 → Run 6，只加 Cosmos，不再同时切 Backbone

Run 6 的设计比 Run 3 更可控：它保留 Run 5 已证明有效的 PaliGemma/action expert 主线，只在旁路增加 Cosmos video expert。用状态转移表示：

\[ \Delta S_6 = \left( D_{\mathrm{future\ frames}}, M_{\mathrm{PaliGemma}}\rightarrow M_{\mathrm{PaliGemma+Cosmos}}, H_{\mathrm{action}}\rightarrow H_{\mathrm{action+video}}, \mathcal{L}_{action}\rightarrow \mathcal{L}_{action}+\lambda_{video}\mathcal{L}_{future}, E_{\mathrm{incomplete}} \right) \]

实现映射：源码 pi0_pytorch_paligemma_cosmos.py 中可见 CosmosVideoExpert、action_in_proj = Linear(32,width)、action_out_proj = Linear(width,32)，以及 future_frame_loss 加入 total_loss。这说明 Run 6 的新增点是 world-model 条件，而不是替换 VLM 主体。

Run 6 的推理去噪过程可写成离散 Euler 更新：

\[ x_{k+1} = x_k - \frac{1}{K} v_\theta(x_k,t_k,o,s,c,z_{\mathrm{video}}), \quad K=10 \]

变量解释：\(x_k\) 是第 \(k\) 个 denoising step 的 32D action chunk，\(K=10\) 对应源码中的 num_steps=10，\(z_{\mathrm{video}}\) 是 Cosmos inference context。实现映射：源码中 dt = -1.0 / num_steps，然后反复执行 x_t = x_t + dt * v_t。

def run6_paligemma_cosmos_branch(observation, model, num_steps=10):
    # 1. Keep the Run 5 perception and action path.
    #    This preserves the PaliGemma pi0.5 prior that already reached 61.875%.
    prefix = model.paligemma_encode(observation.images, observation.prompt)

    # 2. Add Cosmos inference context from the current image and prompt.
    #    Unlike Run 3, the VLM backbone is not replaced by Qwen.
    video_context = model.cosmos.infer_context(
        image=observation.images["image"],
        prompt=observation.prompt,
        num_future_frames=4,
    )

    # 3. Start flow-matching inference from Gaussian noise in 32D action space.
    #    The denoising loop follows the same 32D action contract as Run 5.
    x = sample_standard_normal(shape=(model.action_horizon, model.action_dim))

    # 4. Euler denoising with video-conditioned action expert.
    #    Each step predicts a velocity v and moves x toward the clean action chunk.
    for step in range(num_steps):
        t = 1.0 - step / num_steps
        v = model.action_expert(prefix, observation.state, x, t, video_context)
        x = x - v / num_steps

    # 5. Output transform still slices and denormalizes the first 7D for RoboCasa.
    return model.robocasa_outputs(x)

为什么 60+ 模型有效

这次 60+ 模型的有效改进可以概括为三点。第一，数据格式与 OpenPI π0.5 base 的原始输入输出保持最小偏移：仍然是图像、state、prompt 到连续 action chunk 的 VLA 流程。第二，RoboCasa action 已是 delta，避免了额外 delta/absolute 转换引入的尺度错误。第三，最终 eval 使用固定 seed、固定 layout/style、replan 5 和 image flip，使训练和推理格式尽可能一致。

相反，Qwen+Cosmos 的探索引入了更多潜在不对齐面：不同 VLM tokenizer、世界模型 future-frame loss、多路视觉 slot 复用、Cosmos context 和 action expert 的联合注意力。这些改动在离线 loss 上可收敛，但在闭环控制上更脆弱。
