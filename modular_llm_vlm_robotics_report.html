问题（Question）

本报告回答的问题是：如果不走 VLA（Vision-Language-Action，视觉-语言-动作）或 WAM（World Action Model，世界动作模型）这类端到端“图像/语言直接到动作或未来”的路线，而是把传统机器人算法作为底盘，把 VLM/LLM 作为语义大脑，那么当前研究和工程路线是什么？有哪些代表性项目、数据集、benchmark、系统架构与构成典例值得关注？

这里的“传统算法 + VLM/LLM 大脑”不是指完全不用学习，而是指系统边界不同：LLM/VLM 负责语言理解、开放词表感知、任务分解、语义记忆、约束生成和失败恢复；SLAM、语义地图、任务与运动规划（Task and Motion Planning, TAMP）、Nav2/MoveIt/OMPL、MPC/MPPI、抓取检测、控制器和安全监控负责几何可行性、碰撞约束和闭环执行。

背景与动机（Background & Motivation）

端到端 VLA/WAM 的优点是统一表征、动作学习能力强、容易随着数据规模提升；但它通常需要大量机器人轨迹、动作空间对齐、在线 rollout 验证和模型部署优化。模块化路线的动机相反：把高层语义问题交给基础模型，把连续空间、动力学和安全约束交给可解释、可验证、可替换的传统模块。

从 2022 年 SayCan、Inner Monologue、Code as Policies 到 2023 年 VoxPoser、VLMaps，再到 2024-2026 年开放词表移动操作、3D 场景图、具身问答和多 benchmark 评测，趋势越来越清楚：LLM/VLM 最可靠的位置不是直接输出低层控制量，而是作为“语义接口层”。它把自然语言目标转成技能调用、PDDL/行为树、语义地图查询、对象约束、关键点、候选抓取或失败解释；执行层仍由路径规划、运动规划、抓取和控制闭环完成。

核心判断：当前这条路线更像“机器人系统工程 + 基础模型语义插件”，而不是一个单一模型范式。它在可解释性、低数据启动、真实机器人安全和工程可控性上有优势；在长时程鲁棒性、语义 grounding、接口脆弱性和闭环学习上仍明显受限。

基础概念与术语

端到端 VLA/WAM 与模块化大脑的边界

VLA 通常学习从观测 \(o_t\)、语言指令 \(c\) 到动作 \(a_t\) 或动作块 \(a_{t:t+H}\) 的映射；WAM 进一步把动作、未来观测、世界状态或可行动作后果纳入统一预测。模块化路线则把动作生成拆成语义决策、几何规划和低层控制三层。

专业地说，模块化路线把自然语言任务 \(c\) 分解为离散技能序列 \(\pi_\text{task}\)、连续运动参数 \(\theta\)、目标/约束集合 \(\mathcal{G}\)，再由传统 planner 和 controller 求解可执行轨迹。这使得每个接口可以单独测试，但也要求接口定义足够严格。

任务与运动规划（Task and Motion Planning, TAMP）

直观地说，TAMP 是“先决定做什么，再证明怎么做得到”。例如“把杯子放进柜子”会被拆成 navigate、open_door、grasp、place 等符号动作，同时每个动作都要有可碰撞检测、可逆解、可抓取姿态的连续参数。

专业地说，TAMP 联合搜索符号计划和连续参数。PDDLStream 等框架把传统符号规划器与黑盒采样器/运动规划器连接起来，用 optimistic planning 推迟连续约束的求解，从而处理抓取、放置、轨迹规划等混合离散-连续问题 [38]。

开放词表感知（Open-Vocabulary Perception）

开放词表感知允许机器人用自然语言描述查询对象或地点，例如“红色杯子”“可以坐的东西”“冰箱旁边的台面”。它通常依赖 CLIP、Grounding DINO、SAM、VLM 或 3D 语义特征场，把文本 embedding 与图像/点云/地图 embedding 对齐。

与封闭类别检测不同，开放词表模块的输出不一定是一个固定类别 ID，而可能是对象 mask、3D instance、语义相似度热力图或场景图节点。VLMaps、CLIP-Fields、OpenScene、ConceptGraphs 和 HOV-SG 都属于这一接口方向 [9-13]。

语义地图与 3D 场景图

语义地图（Semantic Map）把空间位置、可通行区域、障碍物、对象实例和语言特征组织成可查询记忆。3D 场景图（3D Scene Graph）进一步显式表示对象、房间、容器、支撑关系、邻接关系和可供性（affordance）。

这类结构是 VLM/LLM 大脑与传统导航/操作算法之间的重要中间层：LLM 负责提出“去哪里/操作什么/为什么”，地图负责给出候选目标，Nav2、A*、RRT、PRM、MPPI 或 MoveIt 负责求解可执行路径。

技能库（Skill Library）与行为树（Behavior Tree）

技能库把复杂控制封装成可调用动作，例如 pick(object_id)、place(surface_id)、navigate(goal_pose)、open(drawer_id)。行为树把技能组织成可中断、可重试、可检查前置条件和后置条件的执行结构。ROS 2 Nav2 官方导航栈就广泛使用行为树来组织导航任务 [41]。

路线之间的共性

  • LLM/VLM 不直接承担所有物理约束。它们负责语义与组合推理，连续几何约束由 motion planner、collision checker 和 controller 验证。
  • 中间表示是成败关键。技能 schema、PDDL、JSON state、scene graph、语义地图、value map、keypoint 都是把“语言”变成“可执行动作”的接口。
  • 评测不应只看最终 success rate。需要拆分为语义理解、对象定位、可达性判断、导航、抓取、放置、恢复次数、人工介入次数和安全违规。

当前能力边界：能演示不等于能部署

本节把“能力”分成三档：工程可靠表示在明确的硬件、场景和工艺条件下可以连续运行；研究可行表示已有论文或项目完成了受控 demo，但仍依赖特定数据、平台或人工恢复；开放问题表示公开系统尚未给出稳定、可重复、可审计的全链路证据。

传统算法的真实上限

传统算法的上限取决于“环境是否可以被工程化”。如果物体类别、工位、相机、机器人、夹具、动作序列和安全边界可以固定，它可以达到很高的稳定性；这就是工业机器人在码垛、焊接、喷涂、上下料和重复装配中仍然占主导的原因。它的弱点不是不会控制，而是无法低成本地解释开放世界目标、自动发现新技能和处理未建模异常。

在家庭机器人中，传统栈通常需要拆成 SLAM/导航、开放词表检测、对象跟踪、抓取、放置、行为树和 recovery policy。每一个模块都可以成熟，但组合后的长时程成功率往往由最弱环节决定。HomeRobot/OVMM、DovSG 等项目体现了这条工程路线：移动底盘、语义地图和机械臂模块分别可用，整机仍需要任务级设计 [8][51]。

VLA 的真实上限

VLA 已经越过“只能做单一实验室动作”的阶段。OpenVLA、π₀、π₀.₅、GR00T N1.7 等系统具备多机器人数据预训练、语言条件控制、跨任务 fine-tuning 和一定的跨场景泛化。它们能在受控条件下完成抓取、放置、清洁、开关抽屉、工具使用，部分系统还能处理较长的家务序列 [45][46][47]。

但 VLA 的证据通常仍有三条边界：第一，动作空间和机器人形态需要适配；第二，复杂能力通常来自 post-training 或特定 checkpoint，而不是基础模型 zero-shot；第三，成功率随摄像头、控制频率、动作归一化、提示词、物体遮挡和 reset 条件变化很大。因此，VLA 更像“可迁移的策略先验”，还不是一个可以取代导航、运动规划和安全监督的万能控制器。

WAM 的真实上限

当前 WAM/世界模型的最强价值主要是预测、模拟、数据生成和策略评价：给定图像、状态和动作，生成未来观测或状态；或者用世界模型产生合成轨迹，再训练 policy。Cosmos 3 把 reasoner、generator 和 action modeling 放进统一的 Physical AI 平台，DreamDojo 使用大规模人类视频预训练机器人世界模型，GR00T-Dreams 则把 Cosmos 视频生成与 inverse dynamics model 连接成合成轨迹管线，PointWorld 进一步预测 RGB-D 场景中的 3D point flow [53][54][55][56]。

这些系统证明了 WAM 路线有助于解决机器人数据稀缺，但尚不能据此宣称“机器人已经学会了物理”。世界模型可能生成视觉上合理但接触力、物体质量、摩擦、遮挡变化不合理的未来；因此当前更可靠的闭环是：真实观测校正世界模型，世界模型提出候选，真实碰撞检查和控制器做最终裁决。

代表项目与系统典例

1. SayCan：语言可行性乘以技能可供性

SayCan 的核心思想是让 LLM 判断“下一步在语言上是否合理”，让低层技能的 affordance 判断“这一步在当前机器人状态下是否可执行”，两者相乘选择技能 [1]。这是一条非常典型的模块化路线：LLM 不生成关节动作，而是在一组可执行技能中做语义调度。

证据：SayCan 项目页和论文公开了 PaLM + affordance skill selection 的设计，并在真实移动机械臂上展示长时程任务执行 [1]。

2. Inner Monologue：用环境反馈闭环修正语言计划

Inner Monologue 把场景描述、成功检测、语言反馈和机器人反馈写回 prompt，让 LLM 在执行过程中“听到自己的内心独白”，从而改进下一步计划 [2]。它证明了模块化路线不能只做 open-loop plan，需要把执行结果、视觉状态和失败信息反馈给大脑。

3. Code as Policies：LLM 生成可执行控制程序

Code as Policies 让语言模型生成 Python 代码，调用已有感知、几何和机器人控制 API [3]。与端到端 VLA 不同，模型输出的是程序结构和 API 调用，真正的控制、检测、运动规划在函数库内完成。它适合 API 稳定、任务可程序化、环境相对结构化的场景。

4. ProgPrompt：程序化 prompt 做家庭任务规划

ProgPrompt 用类似程序的 prompt 表示可调用动作、对象和状态，让 LLM 在 VirtualHome/机器人环境中生成长时程家庭活动计划 [4]。它的价值在于提示工程层面建立了“动作函数 + 前后置条件 + 计划结构”的接口，而不是让模型自由生成自然语言步骤。

5. LM-Nav：LLM 提取 landmark，VLM grounding，经典图导航执行

LM-Nav 面向语言导航：LLM 把自然语言指令解析为地标序列，VLM 把地标 grounding 到视觉观测，导航图/可达性模型负责实际移动 [5]。这是开放词表导航路线的早期典型：语义分解与空间执行解耦。

6. VLMaps、CLIP-Fields、OpenScene、ConceptGraphs：开放词表空间记忆

VLMaps 把语言对齐的视觉特征投影进 3D/2D 空间地图，使机器人可以用文本查询目标区域并调用导航规划 [9]。CLIP-Fields 学习空间中的语言兼容特征场 [10]。OpenScene 把开放词表语义扩展到 3D scene understanding [11]。ConceptGraphs 则从 RGB-D 序列构建开放词表 3D 场景图，显式组织对象实例和关系 [12]。

这些项目构成了“VLM 负责识别和记忆，传统导航负责到达”的主干。它们也把问题从“单帧检测是否正确”变成“地图中语义、几何、拓扑和可达性如何一致”。

7. VoxPoser：LLM/VLM 生成 3D 价值地图，运动规划器执行

VoxPoser 使用 LLM 和 VLM 从语言指令与视觉观测中生成 affordance map 与 constraint map，再把它们组合成 3D value maps，用传统运动规划和控制器求解动作 [6]。这条路线很适合表达“靠近杯柄”“避开盘子”“把物体放到左侧区域”这类几何-语义混合约束。

8. TidyBot 与 OK-Robot：真实家居中的开放词表移动操作

TidyBot 强调个性化整理：通过语言模型从少量用户纠正中学习“物体应该放到哪里”的偏好，再由机器人执行导航、抓取和放置 [7]。OK-Robot 则展示了开放知识、开放词表感知和移动操作系统如何组合到真实家庭场景中，目标是让机器人处理“找某物并移动到某处”这类自然语言任务 [8]。

这类系统最接近真实落地，但也最暴露全链路误差：目标理解、检测分割、语义地图、可达性、抓取姿态、机械臂规划、放置稳定性和失败恢复任一环节出错都会导致任务失败。

9. LLM+P、PDDLStream 与 LLM3：让 LLM 生成，规划器验证

LLM+P 的思路是让 LLM 把自然语言问题翻译成 PDDL，再由经典规划器求解，从而利用 planner 的完备搜索和可验证性 [37]。PDDLStream 则是 TAMP 领域成熟的符号-连续规划框架 [38]。LLM3 等近年工作进一步把 LLM 用于 task-motion planning 和 motion failure reasoning，即在运动规划失败后解释失败并修改计划 [39]。

这条路线的核心不是“LLM 更聪明”，而是“LLM 输出必须被形式化接口约束，再由规划器检查”。如果目标是可靠部署，而不是 demo 式灵活性，这是非常重要的方向。

数学形式与接口目标

1. 技能选择：语言合理性与物理可供性的乘积

令 \(c\) 表示用户指令（command），\(h\) 表示历史执行上下文（history），\(s_t\) 表示当前机器人/环境状态（state），\(\mathcal{K}\) 表示技能集合（skill library），\(u_k\) 表示技能 \(k\) 的语言描述。SayCan 风格选择可写为：

\[ k^\*=\arg\max_{k\in\mathcal{K}} \left[ \log p_{\mathrm{LLM}}(u_k \mid c,h) + \lambda \log q_{\mathrm{aff}}(k \mid s_t) \right] \]

变量解释：\(p_{\mathrm{LLM}}\) 是 LLM 判断“下一步说得通”的概率，\(q_{\mathrm{aff}}\) 是 affordance/value function 判断“当前做得到”的概率，\(\lambda\) 控制语义分数与可执行性分数的权重。

实现映射：工程上可把 \(p_{\mathrm{LLM}}\) 变成候选技能的 log-prob 或排序分，\(q_{\mathrm{aff}}\) 来自技能成功率模型、前置条件检查、几何可达性、导航可达性或 grasp feasibility。该公式对应 SayCan 的核心接口思想 [1]。

2. 语义地图查询：文本目标到可达 goal pose

令 \(q\) 表示文本查询（query），\(e_T(q)\) 表示文本 embedding，\(M(x)\) 表示地图位置 \(x\) 处的视觉-语言特征，\(\Omega_{\mathrm{free}}\) 表示可通行空间，\(d(x,x_t)\) 表示当前位置到候选点的距离，\(r_{\mathrm{risk}}(x)\) 表示障碍/不确定性风险。开放词表导航可抽象为：

\[ x^\* = \arg\max_{x\in\Omega_{\mathrm{free}}} \left[ \cos(e_T(q), M(x)) - \alpha d(x,x_t) - \beta r_{\mathrm{risk}}(x) \right] \]

变量解释：第一项找语义最匹配的位置，第二项惩罚太远的目标，第三项惩罚危险或低置信区域。\(x^\*\) 不是最终控制命令，而是交给 Nav2/A*/局部 planner 的导航目标。

实现映射：VLMaps、CLIP-Fields、ConceptGraphs 等项目都可视为构造 \(M(x)\) 或对象图节点特征；经典导航栈只需要最终 goal pose 和 costmap，因此该接口是模块化路线的关键 [9][10][12][41]。

3. TAMP：符号计划与连续参数联合求解

令 \(\pi=(a_1,\ldots,a_T)\) 表示符号动作序列（symbolic plan），\(\theta=(\theta_1,\ldots,\theta_T)\) 表示连续参数，例如抓取姿态、放置姿态、导航目标、轨迹参数。TAMP 目标可写为：

\[ (\pi^\*,\theta^\*)= \arg\min_{\pi,\theta} C(\pi,\theta) \quad \mathrm{s.t.}\quad \Phi_{\mathrm{sym}}(\pi, s_0, g)=1,\; \Phi_{\mathrm{geom}}(\pi,\theta)=1 \]

变量解释：\(C\) 是代价函数，\(\Phi_{\mathrm{sym}}\) 检查符号前置条件和目标是否满足，\(\Phi_{\mathrm{geom}}\) 检查 IK、碰撞、可达性、抓取稳定性等连续约束。LLM 可以生成 \(g\)、候选 \(\pi\) 或 domain binding，但不应绕过这些约束检查。

实现映射：PDDLStream 把 \(\Phi_{\mathrm{geom}}\) 中的连续可行性检查封装成 stream/sampler，由规划器按需调用；MoveIt/OMPL 可作为 \(\Phi_{\mathrm{geom}}\) 的运动规划后端 [38][42][43]。

4. VLM 价值场到运动规划

令 \(V_\phi(x,q)\) 表示由 VLM/LLM 生成或组合的价值场（value field），\(x_t\) 是机器人末端或物体在时刻 \(t\) 的状态，\(u_t\) 是控制量，\(f\) 是动力学或运动学转移，\(g_{\mathrm{coll}}\) 是碰撞约束。VoxPoser 风格的执行可抽象为：

\[ \tau^\* = \arg\min_{\tau} \sum_{t=0}^{T} \left[-V_\phi(x_t,q)+\rho\|u_t\|_2^2\right] \quad \mathrm{s.t.}\quad x_{t+1}=f(x_t,u_t),\; g_{\mathrm{coll}}(x_t)\le 0 \]

变量解释：高价值区域对应更符合语言目标和视觉约束的位置，控制代价约束动作平滑，碰撞约束保证安全。轨迹 \(\tau^\*\) 仍由优化器、采样 planner 或控制器求解。

实现映射：VoxPoser 将 affordance map、avoidance map、rotation map 等组合为 3D value maps，再通过机器人控制和运动规划执行；这说明 VLM 可以生成“目标函数/约束”，而不必直接输出动作 [6]。

def modular_embodied_agent(user_goal, robot):
    # 1. Read sensors and maintain a geometric/semantic world model.
    obs = robot.sense()
    metric_map = update_slam_and_costmap(obs)
    semantic_map = update_open_vocab_map(obs, metric_map)

    # 2. Convert raw observations into a compact state for the LLM/VLM brain.
    #    The state must be schema-bound; avoid passing unstructured text only.
    state = build_state_json(
        robot_pose=robot.pose,
        objects=semantic_map.visible_objects(),
        rooms=semantic_map.rooms(),
        skills=robot.skill_registry.available_skills(),
    )

    # 3. Ask the brain for a symbolic plan, a behavior tree, or skill call.
    #    The brain may also query the VLM map for candidate objects/regions.
    plan = llm_brain.plan(goal=user_goal, state=state)

    # 4. Validate the plan before execution.
    #    This is where PDDL, behavior-tree guards, reachability, IK, collision
    #    checks, and skill preconditions prevent hallucinated actions.
    validated_plan = planner.verify_and_refine(plan, metric_map, semantic_map)

    # 5. Execute one skill or one small chunk, then observe again.
    for step in validated_plan.steps:
        result = robot.execute_skill(step)

        # 6. Check postconditions with sensors rather than trusting the model.
        if not monitor.check_postcondition(step, result, robot.sense()):
            # 7. Feed structured failure information back to the brain/planner.
            failure = monitor.explain_failure(step, result)
            return modular_embodied_agent(rewrite_goal(user_goal, failure), robot)

    # 8. Final verification matters for benchmarks and real deployment.
    return monitor.check_task_success(user_goal, robot.sense())

开放词表导航 pipeline

def open_vocab_navigation(language_goal, robot, semantic_map, nav_stack):
    # Parse the goal into target concepts and spatial relations.
    query = llm_parse_goal(language_goal)

    # Query a language-indexed map or 3D scene graph.
    candidates = semantic_map.search(
        text=query.target_object,
        room=query.room,
        relation=query.spatial_relation,
    )

    # Filter candidates by reachability and navigation cost.
    feasible_goals = []
    for cand in candidates:
        # Project object or region into a navigable goal pose.
        goal_pose = choose_standoff_pose(cand, semantic_map.costmap)
        if nav_stack.is_reachable(goal_pose):
            feasible_goals.append((goal_pose, cand.semantic_score))

    # Select the best reachable target; then let classical navigation execute.
    goal_pose = rank_by_semantics_and_path_cost(feasible_goals)
    path = nav_stack.plan(goal_pose)
    return nav_stack.follow(path)

抓取放置 pipeline

def open_vocab_pick_place(task_text, robot):
    # Ground object names and spatial relations with a VLM or open-vocabulary detector.
    task = llm_parse_manipulation_task(task_text)
    rgbd = robot.get_rgbd()
    target_mask = vlm_segment(rgbd, text=task.object_query)
    reference_mask = vlm_segment(rgbd, text=task.reference_query)

    # Convert masks into 3D object hypotheses.
    target_cloud = backproject_mask_to_pointcloud(rgbd, target_mask)
    reference_cloud = backproject_mask_to_pointcloud(rgbd, reference_mask)

    # Generate grasp and place candidates with dedicated geometric modules.
    grasps = grasp_planner.propose(target_cloud)
    place_region = compute_language_place_region(
        relation=task.relation,
        reference_cloud=reference_cloud,
    )

    # Validate candidates with IK and collision checks before execution.
    for grasp in rank_grasps(grasps):
        pick_traj = moveit.plan_to_grasp(grasp)
        place_traj = moveit.plan_to_place(place_region)
        if pick_traj.valid and place_traj.valid:
            robot.execute(pick_traj)
            robot.close_gripper()
            robot.execute(place_traj)
            robot.open_gripper()
            return verify_place_relation(task, robot.get_rgbd())

    # If all candidates fail, return structured failure for replanning.
    return {"success": False, "reason": "no collision-free grasp/place plan"}

PDDL/TAMP pipeline

def llm_tamp_solver(language_goal, world_state):
    # LLM produces a symbolic goal and candidate object bindings.
    # The output must be parsed against a fixed schema, not free-form text.
    pddl_problem = llm_translate_to_pddl(language_goal, world_state)

    # Classical planner searches symbolic action sequences.
    candidate_plan = pddl_planner.solve(pddl_problem)

    # Continuous streams sample grasps, poses, and trajectories on demand.
    for action in candidate_plan:
        params = sample_continuous_parameters(action, world_state)
        if not motion_checker.is_feasible(action, params):
            # Add a constraint and replan rather than forcing execution.
            pddl_problem.add_constraint(action, "motion_infeasible")
            return llm_tamp_solver(language_goal, world_state)

    # Execute only after symbolic and geometric feasibility both pass.
    return execute_plan(candidate_plan)

与 VLA/WAM 的互补关系

  • 如果任务需要高频、精细、接触丰富的动作生成，VLA/模仿学习/扩散策略更有优势；模块化路线可以把这些策略作为 skill。

  • 如果目标是工程部署，建议采用“LLM/VLM 负责语义，传统 planner 保底，学习策略做局部技能”的混合架构。

风险与后续建议

主要风险

  • 语义 hallucination。LLM/VLM 可能虚构对象、空间关系或可执行技能；必须通过地图、传感器和 planner 验证。
  • 接口脆弱。自然语言、JSON、PDDL、scene graph、goal pose 之间任何 schema 不一致都会导致系统失败。
  • 开放词表感知与几何不一致。VLM 找到的语义目标可能不可达、被遮挡、pose 不准或不适合抓取。
  • 全链路误差叠加。导航误差、定位误差、mask 误差、抓取误差、放置误差会累积；单模块指标高不代表系统成功。
  • 评测不统一。不同项目任务集、机器人平台、重置条件、失败定义不同，不能直接比较 success rate。
  • 许可和部署约束。公开项目不等于可商用；部分模型、数据、仿真资产和机器人硬件适配需要单独审计。

建议的研究/工程路线

  1. 先做导航闭环：RGB-D/pose 数据构建语义地图，用文本 query 产生 goal pose，再接 Nav2/经典 planner，评测 OVON/GOAT/ObjectNav。
  2. 再做桌面 pick-place：开放词表检测/分割 + GraspNet/AnyGrasp + MoveIt，任务从单物体抓取扩展到空间关系放置。
  3. 引入 LLM planner：把任务状态定义为 JSON schema，技能定义前后置条件，LLM 只输出 schema 内的行为树或 PDDL goal。
  4. 建立错误账本：每次失败标注为语义理解、目标定位、可达性、规划、抓取、放置、控制或监控错误，避免只看总成功率。
  5. 最后考虑与 VLA/WAM 混合：把端到端策略作为局部 skill，而不是一开始就让它接管所有系统边界。
