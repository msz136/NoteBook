1. 问题（Question）

本报告回答一个工程问题：在本地已有 agent 与 19_sensebot_robotics_system 两条项目线的情况下，如何理解 ROS2、机器人/机器狗仿真、模型在环测试与部署之间的关系，并形成一套可复用的生产力流程。

核心结论是：这两个项目覆盖了不同层级的仿真，不应混为一谈。agent 是工具调用与任务状态层的 sandbox，用来验证 LLM Agent 是否会正确调用导航、TTS、拍照、下单、天气等工具；SenseBot 是 ROS2 机器人系统快照，覆盖传感器、感知、SLAM、规划、控制、Unitree SDK、Docker 构建、bag 回灌、PNC 轻量仿真和 Isaac/DLP 模型在环。

2. 背景与动机（Background & Motivation）

机器人仿真的目的不是只做一个“看起来像机器人在动”的画面，而是把真实机器上的风险拆成可重复、可观测、可回放的实验单元。对机器狗尤其如此：导航策略、感知模型、底盘控制、语音/LLM 工具链、传感器驱动和网络中间件都有不同的失败模式。

因此，一条实用的仿真体系通常分成四层：

  1. 工具层仿真：不模拟物理，只模拟 API 返回、工具调用、状态迁移和任务评估，适合训练/评估 Agent。
  2. ROS2 节点层仿真：用 topic、message、launch、bag、bridge 把软件模块连起来，适合查通信契约和模块生命周期。
  3. 模型在环仿真：把感知/规划模型接入 ROS2 输入输出，用录制数据、Isaac 或 synthetic occupancy 验证模型行为。
  4. 物理仿真：用 Gazebo、Isaac Sim/Lab、MuJoCo、Genesis 等模拟动力学、碰撞、传感器和控制闭环。
数据/地图/任务 → fixture 或 bag → 离线评估 → ROS2 节点在环 → 物理仿真 → 小流量实机 → 批量部署 │ │ │ │ │ │ │ │ │ └─ 日志、遥测、故障回灌 │ │ │ └─ Isaac/Gazebo/MuJoCo │ │ └─ DLP/感知/规划节点 │ └─ AceAgent sandbox / rosbag2 └─ 真实地图、传感器数据、任务脚本

3. 基础概念索引

这一节把机器人系统里最容易混在一起的概念拆开讲。它不讨论 LLM/VLM/VLA 模型本身，只解释仿真、ROS、感知、定位建图、规控和部署后端的基础语言。理解这些词之后，再看 agent 和 SenseBot 的项目结构会顺很多。

3.1 一张概念地图

领域核心概念一句话理解
ROS 通信Node、Topic、Message、Service、Action把机器人软件拆成多个进程，用标准消息互相通信。
ROS 运行Parameter、Launch、QoS、tf2、Bag配置、启动、时序、坐标、录制回放这些运行时问题。
仿真Sandbox、Simulator、物理引擎、Bridge、SIL/HIL从“假 API 返回”到“物理世界闭环”的多层替身系统。
感知Sensor、Calibration、Point Cloud、Occupancy、BEV把相机、雷达、IMU 等原始信号变成可规划的空间表示。
定位建图Odometry、Localization、SLAM、Map回答“我在哪、地图是什么、我如何持续更新位置”。
规控Planning、Trajectory、Costmap、Control、PNC从目标点生成路径，再把路径变成机器人能执行的运动命令。
后端部署Workspace、colcon、Docker、Jetson、监控/HMI、ONNX把研发代码变成可构建、可启动、可观测、可部署的机器人服务。

3.2 ROS 通信基础

Node（节点）

节点是 ROS 程序的最小运行单元，通常对应一个进程或进程内组件。例如相机驱动是一个节点，SLAM 是一个节点，规划器也是一个节点。节点之间不直接调用彼此的函数，而是通过 ROS graph 上的通信机制交换消息。这样做的好处是模块可以独立启动、重启、替换和记录。

Topic（话题）

话题是发布/订阅（publish/subscribe）通道，适合连续数据流。相机图像、点云、里程计、局部地图、规划路径都常用 topic。一个节点可以向 /dog_odom 发布里程计，多个节点可以同时订阅它。Topic 名本质上是系统契约：名字、消息类型、频率、坐标系、QoS 都要对上。

Message（消息）

消息是 topic、service、action 传输的数据结构。ROS 有标准消息，如 std_msgs/String、geometry_msgs/PoseStamped、nav_msgs/Odometry、nav_msgs/Path；项目也可以定义自定义消息，如 SenseBot 的 sensebot_msgs/TrajectoryWithTime。消息字段固定，便于跨语言、跨节点通信。

Service（服务）

服务是同步请求/响应接口，适合“问一次、答一次”的操作。例如查询地图列表、重置状态、开关某个功能。它不像 topic 那样持续流动，而是客户端发请求，服务端返回结果。服务适合短任务，不适合导航这种持续几十秒且需要反馈/取消的任务。

Action（动作）

动作是 ROS 中处理长任务的通信模式，包含 goal、feedback、result 和 cancel。导航到目标点、机械臂抓取、长时间扫描都适合 action。它比 service 更适合机器人任务，因为任务执行中可以持续反馈进度，也可以被取消。

Parameter（参数）

参数是节点的运行配置，例如发布频率、地图分辨率、传感器外参文件路径、规划器阈值。参数可以由 YAML、launch 文件或命令行传入。仿真环境常通过参数切换地图大小、机器人初始位姿、是否开启传感器模拟。

Launch（启动系统）

Launch 文件负责一次性启动多个节点、设置参数、命名空间、remap 和环境变量。真实机器人不是手动开十几个终端运行节点，而是用 launch 或脚本编排。SenseBot 的 setup_and_launch.sh 实际上就是把 statemachine、SLAM、perception、planning、control 等节点按生产方式拉起来。

QoS（Quality of Service，服务质量）

QoS 决定消息传输策略，例如可靠传输还是尽力而为、队列深度是多少、是否保留最后一条消息。相机/点云高频数据常用 best effort，配置/状态类消息更偏 reliable。仿真和实机出现“topic 明明有发布但订阅不到”时，QoS 不匹配是常见原因。

tf2（坐标变换系统）

tf2 维护机器人各坐标系之间的时变关系，例如 map、odom、base_link、camera_link、lidar_link。感知、SLAM 和规划必须知道同一个点在不同坐标系下的位置，否则地图会漂、障碍物会错位、规划轨迹也会错。tf2 是机器人系统里最基础也最容易出错的部分之一。

Bag / rosbag2（数据包、录制回放）

Bag 是 ROS 的“黑匣子录音”。它把一段时间内多个 topic 的消息按时间戳录下来，之后可以像真实传感器一样回放。一个 bag 可能包含 /camera/color/image_raw、/dog_odom、/perception/occ3d、/slam/localization_stateinfo 等。生产上 bag 很重要，因为它能把实机问题冻结下来：同一段数据可以反复喂给新版本感知、SLAM 或规划代码。

DDS 与 ROS_DOMAIN_ID

DDS（Data Distribution Service）是 ROS2 底层通信机制。ROS_DOMAIN_ID 用来隔离不同 ROS2 网络域；同一个 domain 内的节点能互相发现，不同 domain 通常互不可见。SenseBot DLP 的仿真测试把 ROS_DOMAIN_ID 设为 60，就是为了让 Isaac、DLP、planning、control 处在同一个 ROS2 通信域。

3.3 ROS 工程基础

Workspace（工作空间）

ROS2 workspace 是一组 package 的开发根目录，常见结构是 ros_ws/src/package_name。构建后会生成 build/、install/、log/。运行前通常要 source install/setup.bash，这样 shell 才能找到新编译的 package、消息类型和可执行文件。

Package（功能包）

Package 是 ROS2 代码组织单元。一个 package 可以包含节点源码、消息定义、launch 文件、配置文件和资源。SenseBot 里 perception、slam、planning、control、sensebot_msgs 都是不同功能包。

colcon（构建工具）

colcon 是 ROS2 常用构建工具，负责按依赖顺序编译多个 package。SenseBot 的 Makefile 本质上是在不同平台、不同 ROS 版本、不同 package 集合上封装 colcon build。当只改一个包时，可以用 colcon build --packages-select package_name 缩短迭代时间。

Remap（重映射）

Remap 是把节点内部使用的 topic 名换成系统中的另一个 topic 名。例如 simulator 发布 /simulator/robot_pose，launch 中可以 remap 到 /dog_odom，让下游节点以为数据来自真实机器人里程计。Remap 很有用，但也很脆弱：源 topic 拼错，整个链路就会沉默。

3.4 仿真基础

Sandbox（沙盒）

Sandbox 是受控实验环境。它可以完全不模拟物理，只模拟 API、状态机和评估函数。agent 的 sandbox 就是这种：导航工具不会真的让机器狗移动，而是更新虚拟位置、记录工具调用、计算轨迹 loss。它适合验证上层决策逻辑，不能证明真实运动安全。

Simulator（仿真器）

Simulator 是更广义的仿真运行环境，可以模拟状态、传感器、地图、物理、机器人运动或网络通信。SenseBot 的 PNC simulator 模拟的是 heightmap 与 odometry；Isaac/Gazebo/MuJoCo 模拟的层次更深，可以包含视觉、雷达、碰撞和动力学。

物理引擎、动力学与碰撞

物理引擎负责计算刚体运动、关节、接触、摩擦、碰撞和重力。机器狗比轮式机器人更依赖物理仿真，因为足端接触、打滑、跌倒、姿态稳定都会影响策略是否可用。MuJoCo 和 Isaac Lab 常用于这类接触丰富的控制训练。

传感器仿真

传感器仿真生成虚拟相机图像、深度图、LiDAR 点云、IMU、GNSS 等。高保真传感器仿真能测试感知模型，但成本高；低保真 synthetic 数据便宜，但容易和真实数据分布不一致。生产中常把传感器仿真和真实 bag 回放结合使用。

Digital Twin（数字孪生）

数字孪生是尽量还原真实场地、机器人模型、传感器位置、动力学和任务流的仿真系统。它比普通 demo 场景要求更高：地图尺寸、材质、障碍物、光照、传感器外参、机器人质量和控制参数都要接近实机。

Bridge（桥接）

Bridge 把两个系统的通信协议连接起来。例如 ros_gz 把 Gazebo 和 ROS2 topic 接起来，Isaac ROS2 Bridge 把 Isaac 场景里的传感器和 ROS2 节点接起来，agent_sandbox_bridge 把 AceAgent 2D sandbox 接成 ROS2 topic。Bridge 的核心问题是消息类型、时间戳、坐标系和频率是否一致。

SIL / HIL / MIL（软件、硬件、模型在环）

SIL（Software-in-the-Loop）是软件在环：真实控制软件跑起来，但输入来自仿真或回放。HIL（Hardware-in-the-Loop）是硬件在环：部分真实硬件也接入闭环，例如控制板或传感器。MIL（Model-in-the-Loop）是模型在环：感知或规划模型接入仿真/回放流程，验证模型输出对系统的影响。SenseBot 的 DLP + Isaac 流程就是典型模型在环。

3.5 感知与空间表示基础

Sensor（传感器）

机器人常见传感器包括 RGB/RGBD 相机、LiDAR、IMU、GNSS、轮速/关节编码器。相机提供纹理和语义，LiDAR 提供几何距离，IMU 提供角速度和加速度，GNSS 提供室外全局位置。不同传感器的频率、延迟、噪声和坐标系都不同。

Calibration（标定）

标定包括内参和外参。内参描述相机焦距、畸变等自身参数；外参描述相机、雷达、IMU 相对机器人底盘的位置和朝向。标定错了，点云投影、相机融合、占据栅格都会偏。SenseBot 启动脚本里反复设置 calibration，正是因为它是生产系统的地基。

Point Cloud（点云）

点云是一组 3D 点，常来自 LiDAR 或深度相机。每个点通常包含 \(x,y,z\)，可能还有 intensity、ring、timestamp。点云适合几何建图和障碍物检测，但数据量大，需要滤波、配准、体素化和坐标变换。

Occupancy Grid / Voxel Grid（占据栅格 / 体素栅格）

占据栅格把空间切成格子，每个格子表示是否被障碍物占据，或者属于道路、草地、楼梯、路沿等类别。2D occupancy grid 用于平面导航；3D voxel grid 能表达高度和立体结构。SenseBot 感知输出的 /perception/occ3d 和 /perception/occ3d_single 就是这类空间表示。

BEV（Bird's-Eye View，鸟瞰图）

BEV 是从上往下看的空间表示。自动驾驶和机器人规划常把相机/雷达信息投到 BEV，因为规划器更关心地面平面上的可通行区域、障碍物和路线。BEV 的优势是和路径规划天然对齐，缺点是要处理高度、遮挡和传感器融合误差。

Costmap（代价地图）

代价地图是在 occupancy 或语义地图上进一步计算出来的规划地图。障碍物附近代价高，可通行区域代价低，未知区域可按策略设为高代价或中等代价。局部规划器会在 costmap 上寻找低风险轨迹。机器狗还可能把坡度、高度差、楼梯、草地等加入代价。

Heightmap（高度图）

Heightmap 是每个平面网格对应一个高度值的地图。它适合表达坡、台阶、矮障碍。SenseBot 的 PNC simulator 会创建全局 heightmap，设置矩形障碍物，再根据机器人位姿裁出局部 heightmap 发布给下游。

3.6 定位、建图与运动状态

Odometry（里程计）

里程计估计机器人相对运动，常来自轮速、IMU、视觉、LiDAR 或腿部运动估计。它短期平滑，但长期会漂移。ROS 中 nav_msgs/Odometry 通常包含 pose、twist 和协方差。SenseBot 将 simulator 的 /simulator/robot_pose remap 到 /dog_odom，就是为了模拟里程计输入。

Localization（定位）

定位是在已有地图或全局坐标中估计机器人当前 pose。它回答“我在地图中的哪里”。定位可能融合 GNSS、IMU、LiDAR map matching、视觉特征等。定位质量直接影响规划：位置偏了，目标点和障碍物都会偏。

SLAM（Simultaneous Localization and Mapping，同步定位与建图）

SLAM 同时估计机器人轨迹和环境地图。它常用于未知或半未知环境。SenseBot 的 SLAM 输出包括 /slam/odom_stateinfo、/slam/localization_stateinfo 和 /slam/nav_map，下游规划和感知都依赖这些结果。

Map（地图）

地图可以是几何点云、2D 栅格、3D voxel、语义地图、拓扑点位图或导航路线图。agent 的 xian_10th fixture 更接近“点位/语义地图”；SenseBot 更接近“传感器建图 + 导航地图 + 规划代价地图”。不同地图服务不同层级，不能用一种地图概念解释所有模块。

3.7 规划与控制基础

Planning（规划）

规划负责从当前状态到目标状态生成可执行方案。全局规划关注从 A 到 B 的大路线；局部规划关注短时间内如何绕障、平滑和避碰。规划输入通常包括目标点、地图、定位、障碍物、机器人运动约束，输出是 path 或 trajectory。

Path 与 Trajectory（路径与轨迹）

Path 通常只是一串空间点，表示走哪条线；trajectory 还包含时间、速度、加速度或姿态，表示什么时候以什么状态到达每个点。SenseBot 的 TrajectoryWithTime 就是带时间的轨迹，PNC simulator 可以按时间插值机器人位置。

Global Planner 与 Local Planner（全局/局部规划器）

全局规划器在较大地图上找路线，常用 A*、Dijkstra、Hybrid A* 等；局部规划器在机器人附近根据动态障碍和运动学限制生成短期轨迹，常见方法包括 DWA、TEB、MPC。SenseBot README 提到 planning 使用 TEB local planner，这是局部轨迹优化的一类方法。

Control（控制）

控制把规划轨迹转成机器人底层命令，例如速度、姿态、关节目标或电机指令。轮式机器人通常输出线速度/角速度；机器狗还涉及步态、足端力、姿态稳定和底层 SDK。SenseBot 的 control 包通过 Unitree SDK2 接到底层机器人。

PNC（Planning and Control，规划与控制）

PNC 是规划与控制的合称。在机器人系统里，PNC 层通常连接地图/感知/定位与底盘控制：它既要知道哪里能走，也要知道机器人怎么走得稳。SenseBot 的 src/pnc 包含规划控制相关代码和轻量 simulator。

State Machine（状态机）

状态机负责管理机器人任务状态，例如 idle、navigating、paused、charging、error。它把多个节点的信号组织成产品行为。没有状态机，感知、规划、控制可能都能跑，但系统不知道当前应该响应用户任务、避障、停止还是恢复。

3.8 后端、部署与观测基础

后端服务

机器人后端负责把机器人能力变成网络 API 或管理系统：鉴权、任务下发、工具路由、状态缓存、日志、模型选择、设备绑定、HMI 数据转发都属于后端范畴。agent 就是偏后端/Agent runtime 的项目，SenseBot 则更偏机器人端运行时。

Docker / 容器

Docker 把编译环境、系统依赖、CUDA、ROS2、Python 包固定下来。机器人项目依赖复杂，容器能避免“这台机器能编，那台不能编”。SenseBot 明确要求构建和运行命令在 Docker 容器内执行，说明它把容器当作生产环境边界。

Jetson / Orin / aarch64

Jetson Orin 是 NVIDIA 面向边缘 AI 和机器人的计算平台，aarch64 是其 CPU 架构。x86 开发机和 Jetson 目标机架构不同，所以 SenseBot Makefile 区分 x86 构建和 ARM 交叉编译。涉及传感器、CUDA、第三方库时，平台差异会非常实际。

日志、监控与 HMI

日志记录节点输出和错误，监控关注 CPU/GPU/内存/进程/温度，HMI（Human-Machine Interface）提供人机界面。机器人调试离不开这些，因为现场问题往往不是算法单点错误，而是进程没启动、topic 断流、传感器掉线、资源打满或网络不通。SenseBot 的 rosboard/web_visual、monitor、diag_monitor 都属于这条线。

ONNX 与模型部署

ONNX 是模型交换格式，用来把训练框架里的模型导出到更适合部署的推理引擎。DLP 的 export_onnx.py 把 PyTorch planning model 导出为 ONNX，并保存输入输出样例与 checker 校验结果。实际量产还可能继续转 TensorRT 或其他加速格式。

OTA 与打包

打包是把编译产物、配置、脚本整理成可部署压缩包；OTA（Over-the-Air）是远程更新机器人软件。SenseBot 的 pack.sh 生成 sensebot.tar.gz，再拷贝到 Go2 Orin 上解压运行。这一步决定了研发代码能否稳定进入设备。

4. ROS 是什么

机器人操作系统（Robot Operating System, ROS）不是传统意义上的操作系统，而是一套机器人软件中间件：它提供节点（Node）、话题（Topic）、服务（Service）、动作（Action）、参数（Parameter）、启动系统（Launch）、坐标变换（tf2）、日志和 bag 录制回放等机制。ROS2 在通信层使用 DDS（Data Distribution Service），适合分布式、多进程、实时性更强的机器人系统。

4.1 ROS2 图模型

ROS2 程序由一组节点组成。节点通过 topic 发布/订阅连续数据，通过 service 做同步请求/响应，通过 action 执行可取消、可反馈的长任务。典型导航链路如下：

/camera, /lidar, /imu
      ↓
perception_node  → /perception/occ3d
slam_node        → /slam/localization_stateinfo, /dog_odom
planning_node    → /planning/path 或 /pnc_planner_path_with_time
control_node     → Unitree SDK2 / motor command
      ↓
robot

4.2 坐标系与局部地图

仿真和真实机器人都会不断做坐标转换。若机器人在世界坐标中的位姿为 \((x_r, y_r, \theta_r)\)，世界点 \(p_w=(x_w,y_w)\) 转到机器人局部坐标可写为：

\[ p_{ego} = \begin{bmatrix} \cos\theta_r & \sin\theta_r \\ -\sin\theta_r & \cos\theta_r \end{bmatrix} \left( \begin{bmatrix}x_w\\y_w\end{bmatrix} - \begin{bmatrix}x_r\\y_r\end{bmatrix} \right) \]

SenseBot 的 PNC simulator 正是在这个意义上从全局 heightmap 按机器人 pose 裁出局部 heightmap，再发布给规划/控制链路。

4.3 rosbag2 为什么重要

rosbag2 是 ROS2 的数据录制与回放机制。它让真实机器上的传感器、定位、规划输出变成可复现实验。生产中常见做法是：实机采集 bag，离线回放给感知/SLAM/规划节点，保存日志与轨迹，再把失败片段转成回归测试。

5.3 评估公式

score_trace() 的综合 loss 可抽象为：

\[ L = w_s L_{seq} + w_a L_{arg} + w_f L_{forbid} + w_t L_{text} + w_r L_{state} + w_b L_{behavior} \]

当存在状态检查时，源码使用的权重是 \(w_s=0.35, w_a=0.25, w_f=0.15, w_t=0.05, w_r=0.10, w_b=0.10\)。没有状态检查时，序列和参数权重分别提高到 0.40 和 0.30。

6.8.1 结论：路径和主要避障在 planning，但安全闭环跨模块

SenseBot 中的路径演算、局部避障、轨迹生成主要落在 planning 模块；但“避障能力”不是单个 planning 文件独立完成的。感知提供障碍物和占据栅格，SLAM/定位提供机器人当前位姿和速度，状态机提供任务目标与模式，planning 把这些信息变成带时间的轨迹，control 再把轨迹跟踪成 vx / vy / vyaw 速度命令。

模块它提供什么它不主要负责什么
statemachine发布 /state_change，说明当前任务是室外、室内、定点、动态导航等。不计算路径，不直接控制底盘速度。
perception发布 /perception/occ3d_single、/perception/occ3d_lidar、/perception/objects 等障碍与目标信息。不决定“绕哪边走”。
slam/localization发布定位、里程计、地图相关状态，告诉下游“我在哪里、我怎么动”。不选择导航路线。
planning订阅任务、定位、占据栅格和目标物，生成 path、obstacle debug、PNC 状态和 /pnc_planner_path_with_time。不直接调用机器狗 SDK。
control订阅 /pnc_planner_path_with_time 和定位，跟踪轨迹并输出速度命令。通常不重新做全局找路。
Unitree SDK2 / device interface把 Move(vx, vy, vyaw) 这类请求发给机器狗底层运动控制。不理解高层导航目标和地图。
StateChange + Localization + OCC/Objects ↓ planning: 任务解析 → 地图/障碍预处理 → 路径搜索 → 轨迹优化 ↓ /pnc_planner_path_with_time ↓ control: 轨迹跟踪/MPC → vx, vy, vyaw ↓ Unitree SportClient::Move(vx, vy, vyaw)

6.8.2 StateChange 是任务状态，不是速度命令

StateChange 消息包含 state、id、description 三类核心字段。state 表示 IDLE、COMPANION、NAVIGATION、ACTION、ERROR、MAPPING、RELOCATION、VLN、CHARGING 等产品状态；id 是状态切换次数；description 是 JSON 字符串，用来携带导航模式和任务上下文，例如 mode、route_json、destination、map_path、localization_mode、detection_type。

因此，StateChange 的作用更像“任务开关和任务说明书”：它告诉 planning 现在要进入哪类导航任务，以及目标、路线、地图在哪里。它不是 vx、vy、vyaw，也不是底盘控制命令。planning 会把 description.mode 中的 OUTDOOR、INDOOR、FIXED_POINT、DYNAMIC 转成内部 planning 状态。

StateChange.description
  mode = OUTDOOR       → planning state: NAVIGATION
  mode = INDOOR        → planning state: INDOOR_NAVIGATION
  mode = FIXED_POINT   → planning state: FIXED_POINT_NAVIGATION
  mode = DYNAMIC       → planning state: DYNAMIC_NAVIGATION

6.8.3 planning 周期：每 0.1 秒重算一次局部未来

planning_conf.pb.txt 中 planning_period: 0.1，说明规划周期约为 10Hz。配置里还出现 total_time: 6.0、delta_t: 0.2、obs_stop_distance: 0.5 等参数，可以理解为：每次规划都生成未来数秒的轨迹，并按离散时间点表达，同时保留障碍停车距离等安全约束。

主循环由 PlanningRegulator::Proc() 串起来：先创建当前 Frame，把最新 ROS 消息和上一帧结果放进去；再做预处理、远程动作执行、状态机 pipeline、后处理；任何关键环节失败时进入 fail-safe，生成保守轨迹或停车轨迹。

function planning_cycle():
    frame = collect_latest_messages()
    frame.pose = localization_state
    frame.task = state_change
    frame.occ3d = perception_occ3d
    frame.objects = perception_objects
    frame.last_result = previous_planning_output

    if diagnose(frame) fails:
        return fallback_stop()

    preprocess(frame)          # OCC/点云/障碍物 → 2D costmap
    execute_remote_action(frame)
    state_manager.execute(frame)
        pipeline = select_pipeline(frame.task.mode)
        for task in pipeline:
            task.execute(frame)
    postprocess(frame)

    publish(frame.planning_output.trajectory_with_time)

6.8.4 导航能力：先回答“往哪走”

这里的导航不是一个单独算法，而是不同任务形态下的“目标解释 + 路径初始化”。室内导航会基于离线地图或局部地图做 A* 搜索；室外导航会把 route_json / 高德路线处理成 UTM/Frenet 参考线，再生成局部可跟踪路径；定点和动态导航则围绕目标点或目标物构造初始路径。

模式pipeline 配置路径初始化思路
室外导航OUTDOOR → ILQR_PLANNER处理 route_json，构建 Frenet 参考线，生成局部路径，再交给 ILQR 优化。
室内导航INDOOR → ILQR_PLANNER在室内地图/局部地图上用 A* 类搜索得到初始路径，再交给 ILQR 优化。
定点导航FIXED_POINT → TEB_PLANNER从当前位姿到目标点生成初始路径，再用 TEB 做局部时间弹性优化。
动态导航DYNAMIC → TEB_PLANNER围绕动态目标更新目标点和初始路径，再用 TEB 持续优化。
伴随模式FOLLOW → TEB_PLANNER跟随目标对象，偏局部目标追踪和局部避障。
 
function navigation_task(frame):
    mode = parse(frame.state_change.description.mode)

    if mode == INDOOR:
        map = load_indoor_map(frame.map_path)
        init_path = astar_search(map, frame.pose, frame.destination)

    else if mode == OUTDOOR:
        route = parse_route_json(frame.route_json)
        reference = build_frenet_reference(route)
        init_path = sample_local_path(reference, frame.pose)

    else if mode == FIXED_POINT:
        init_path = connect_pose_to_goal(frame.pose, frame.destination)

    else if mode == DYNAMIC:
        target = estimate_dynamic_target(frame.objects, frame.detection_type)
        init_path = connect_pose_to_target(frame.pose, target)

    frame.init_path = init_path

6.8.5 避障能力：不是“看到障碍就躲”，而是把障碍变成代价和约束

SenseBot 的避障信息先来自感知输出。preprocess.cc 会把 /perception/occ3d_single 和 /perception/occ3d_lidar 转成 Occ2d，再转成 Costmap2D，分别放入 obstacle_avoid_costmap_ 和 heightmap_costmap_。这一步是规划能避障的前提：规划器不直接处理原始相机图像，而是处理已经结构化的占据、代价和目标物。

进入 motion planner 后，ILQR 路线会进一步做静态障碍提取、动态障碍加入、障碍轨迹预测、costmap 膨胀与融合、走廊构造和碰撞检查；TEB 路线则把初始路径、机器人状态、障碍物和速度限制放进时间弹性带优化器中。简化理解：避障不是一个“avoid()”函数，而是一组贯穿预处理、搜索、优化和 fail-safe 的约束。

function obstacle_avoidance(frame):
    occ2d_camera = project_occ3d_to_2d(frame.perception_occ3d)
    occ2d_lidar = project_lidar_occ3d_to_2d(frame.lidar_occ3d)

    costmap_obs = convert_occ2d_to_costmap(occ2d_camera)
    costmap_height = convert_occ2d_to_costmap(occ2d_lidar)

    static_obstacles = extract_obstacles(costmap_obs)
    dynamic_obstacles = filter_and_predict(frame.perception_objects)

    inflated_costmap = inflate_and_merge(costmap_obs, dynamic_obstacles)

    frame.obstacles = static_obstacles + dynamic_obstacles
    frame.costmap = inflated_costmap

6.8.6 规划能力：ILQR、Hybrid A* 与 TEB 各司其职

室内/室外导航主要配置为 ILQR_PLANNER。它的代码结构很典型：先做障碍处理，再构造 nominal path，再做速度层障碍处理和 nominal speed，最后联合优化轨迹并后处理。局部路径生成中还会用 HybridAStarOCC 生成满足朝向和占据约束的 nominal path；速度障碍处理中也出现 HybridAStarST 这类时空搜索思想。

定点、动态、伴随等任务主要配置为 TEB_PLANNER。TEB（Timed Elastic Band，时间弹性带）可以把路径看成一串带时间间隔的姿态点，通过优化这些姿态点和时间间隔，让轨迹同时满足避障、速度、转向、平滑性等约束。它适合短视野、目标持续变化、需要滚动优化的局部导航。

function ilqr_planner(frame):
    obstacles = build_path_obstacles(frame.costmap, frame.objects)

    frenet = build_frenet(frame.init_path)
    nominal_path = hybrid_astar_occ(frenet, frame.costmap, frame.pose)
    corridor = build_static_corridor(nominal_path, frame.costmap)

    speed_constraints = check_static_and_dynamic_collision(
        nominal_path,
        obstacles,
        frame.speed_limit
    )

    nominal_speed = compute_reference_speed(frame.target_speed, speed_constraints)

    trajectory = joint_optimize_path_and_speed(
        nominal_path,
        nominal_speed,
        corridor,
        obstacles,
        robot_kinematics
    )

    return postprocess_trajectory(trajectory)
function teb_planner(frame):
    band = initialize_timed_elastic_band(frame.pose, frame.init_path)
    obstacles = convert_costmap_and_objects_to_teb_obstacles(frame.costmap, frame.objects)

    repeat until convergence or max_iter:
        add_cost(band close to init_path)
        add_cost(no collision with obstacles)
        add_cost(velocity and angular_velocity limits)
        add_cost(acceleration and smoothness limits)
        optimize_band_pose_and_time()

    return convert_band_to_trajectory_with_time(band)

6.8.7 控制能力：最终给机器狗的是速度，但速度来自轨迹跟踪

最终给 Go2 的调用确实是速度形式：SportClient::Move(vx, vy, vyaw)，并且控制节点也发布 /unitree_go2/cmd_vel 这样的速度消息用于观测或兼容。但这些速度不是 Agent 直接写出来的，也不是状态机直接给出的；它们来自 planning 生成的 TrajectoryWithTime，再由 control 根据当前定位状态做轨迹跟踪。

TrajectoryWithTime 消息包含 trajectory_points、trajectory_rpys、trajectory_vels、trajectory_angular_vels、timestamps、total_duration、num_points 等字段。control 每个周期根据“当前时刻机器人在哪里”和“规划轨迹此时希望机器人在哪里/多快”计算速度命令。由于 planning 约 10Hz 滚动重算，速度会被持续更新和维护，而不是一次导航开始时生成一组固定速度跑到底。

function control_cycle():
    traj = latest("/pnc_planner_path_with_time")
    pose = latest_localization()

    target_point = sample_trajectory_by_time(traj, now)
    station_error = target_point.pose - pose
    speed_error = target_point.velocity - pose.velocity

    vx, vy, vyaw = mpc_or_tracking_controller(
        station_error,
        speed_error,
        target_point,
        robot_limits
    )

    if trajectory_invalid_or_timeout:
        vx, vy, vyaw = 0, 0, 0

    publish_unitree_request(SportClient.Move(vx, vy, vyaw))

6.8.8 Agent 调 nav 与 Bot 调机器的层级不同

从 agent 项目看，nav 是一个高层工具能力：Agent 说“导航到某点”，sandbox 更新虚拟位姿、记录调用轨迹、计算任务是否完成。这是任务层/后端层的原子能力，适合评估模型有没有正确用工具。

SenseBot 这一侧不是再去调用一个同名的“nav 工具”。它的原子能力更接近 ROS2 graph 内部的节点协作：状态机广播任务，planning 根据感知、定位和地图生成轨迹，control 跟踪轨迹并通过 Unitree SDK2 发速度。也就是说，bot 项目最终是通过底层运动接口操控机器狗；导航只是它在 ROS2 系统中组合出来的一条闭环能力链。

Agent 层 nav 工具: navigate_to("小卖部") → sandbox/API 状态更新 SenseBot 端侧导航链: StateChange(NAVIGATION, description) → planning pipeline → TrajectoryWithTime → control tracking → SportClient::Move(vx, vy, vyaw)

6.8.9 四个能力的最小心智模型

能力输入核心算法思想输出
导航目标、地图、任务模式把产品目标翻译成可规划的参考路径；室内偏 A*，室外偏 route/Frenet，动态目标偏实时目标更新。init_path 或参考线。
规划初始路径、位姿、速度、代价地图、障碍物用搜索和优化把“能走的路径”变成“可执行的时序轨迹”。TrajectoryWithTime。
避障OCC、点云、目标物、costmap把障碍物转成栅格代价、几何障碍、时空约束和碰撞惩罚，必要时触发停车。避障后的路径/轨迹约束。
控制规划轨迹、当前定位、机器人运动限制轨迹跟踪/MPC，根据误差持续计算底盘速度。vx / vy / vyaw。

所以，回答“系统的避障/路径演算是不是都通过规划模块完成”：工程上可以说主要通过 planning 完成，但不要把它理解成 planning 单独拥有全部信息和全部安全责任。更准确的说法是：感知发现世界，定位确定自身，状态机给任务，planning 计算可行轨迹，control 把轨迹维持成速度，底层 SDK 执行动作。

8. 机器人/机器狗仿真的生产力流程

8.1 从最小可复现开始

  1. 定义任务契约：用户指令、地图点位、允许工具、禁止工具、预期状态、成功指标。
  2. 做 fixture/sandbox：先用离线地图和模拟状态验证 LLM 或调度器是否会按正确顺序调用工具。
  3. 接 ROS2 bridge：把 sandbox 的状态和目标暴露成 topic，开始检查消息类型、topic 名和 launch 组织。
  4. 引入 bag 回灌：用真实传感器和定位数据驱动感知/SLAM/规划，避免只在 synthetic 场景中自洽。
  5. 模型在环：把 DLP、OCC、VLN/VLA 模型作为 ROS2 节点接入，记录输入输出和延迟。
  6. 物理仿真：用 Isaac/Gazebo/MuJoCo 检查传感器模拟、碰撞、足式动力学和控制闭环。
  7. 实机灰度：在低风险场景、低速度、可急停条件下部署，失败日志回灌到前面几层。

9. 方法对比与选择建议

目标优先环境原因不适合做什么
评估 LLM Agent 是否会正确用工具AceAgent sandbox成本低、可批量、可给轨迹 loss。不能证明物理安全、避障和运动控制正确。
检查 ROS2 模块通信ROS2 bridge / launch / rosbag2直接暴露 topic、message、QoS、启动顺序。不能自动覆盖传感器真实性和动力学。
回归真实道路/园区数据bag replay最接近线上问题，便于复现。不能探索没有采集过的新场景。
训练/验证感知与规划模型OCC/DLP 离线评估 + Isaac 模型在环既有指标又能接 ROS2 闭环。如果没有物理闭环，不能验证底盘动态。
机器狗 locomotion 和接触控制MuJoCo / Isaac Lab / Unitree RL Gym需要接触动力学和大量并行 rollouts。不擅长直接替代 ROS2 生产系统部署。
端到端产品部署Docker + colcon + pack + 实机灰度贴近 SenseBot 当前生产形态。风险高，必须前置 sandbox、bag、仿真验证。
建议路线：先用 agent 的 sandbox 建立任务级回归集，再把关键任务通过 ROS2 bridge 接到最小 ROS graph；随后用 SenseBot 的 bag replay 和 DLP/Isaac 流程做模型在环；最后再进入 Unitree 实机与 Docker 打包部署。这样每一层失败都有可回放证据。
