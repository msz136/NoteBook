1. 问题（Question）

本报告回答一个工程问题：在本地已有 agent 与 19_sensebot_robotics_system 两条项目线的情况下，如何理解 ROS2、机器人/机器狗仿真、模型在环测试与部署之间的关系，并形成一套可复用的生产力流程。

核心结论是：这两个项目覆盖了不同层级的仿真，不应混为一谈。agent 是工具调用与任务状态层的 sandbox，用来验证 LLM Agent 是否会正确调用导航、TTS、拍照、下单、天气等工具；SenseBot 是 ROS2 机器人系统快照，覆盖传感器、感知、SLAM、规划、控制、Unitree SDK、Docker 构建、bag 回灌、PNC 轻量仿真和 Isaac/DLP 模型在环。

2. 背景与动机（Background & Motivation）

机器人仿真的目的不是只做一个“看起来像机器人在动”的画面，而是把真实机器上的风险拆成可重复、可观测、可回放的实验单元。对机器狗尤其如此：导航策略、感知模型、底盘控制、语音/LLM 工具链、传感器驱动和网络中间件都有不同的失败模式。

因此，一条实用的仿真体系通常分成四层：

  1. 工具层仿真：不模拟物理，只模拟 API 返回、工具调用、状态迁移和任务评估，适合训练/评估 Agent。
  2. ROS2 节点层仿真：用 topic、message、launch、bag、bridge 把软件模块连起来，适合查通信契约和模块生命周期。
  3. 模型在环仿真：把感知/规划模型接入 ROS2 输入输出，用录制数据、Isaac 或 synthetic occupancy 验证模型行为。
  4. 物理仿真：用 Gazebo、Isaac Sim/Lab、MuJoCo、Genesis 等模拟动力学、碰撞、传感器和控制闭环。
数据/地图/任务 → fixture 或 bag → 离线评估 → ROS2 节点在环 → 物理仿真 → 小流量实机 → 批量部署 │ │ │ │ │ │ │ │ │ └─ 日志、遥测、故障回灌 │ │ │ └─ Isaac/Gazebo/MuJoCo │ │ └─ DLP/感知/规划节点 │ └─ AceAgent sandbox / rosbag2 └─ 真实地图、传感器数据、任务脚本

3. ROS 是什么

机器人操作系统（Robot Operating System, ROS）不是传统意义上的操作系统，而是一套机器人软件中间件：它提供节点（Node）、话题（Topic）、服务（Service）、动作（Action）、参数（Parameter）、启动系统（Launch）、坐标变换（tf2）、日志和 bag 录制回放等机制。ROS2 在通信层使用 DDS（Data Distribution Service），适合分布式、多进程、实时性更强的机器人系统。

3.1 ROS2 图模型

ROS2 程序由一组节点组成。节点通过 topic 发布/订阅连续数据，通过 service 做同步请求/响应，通过 action 执行可取消、可反馈的长任务。典型导航链路如下：

/camera, /lidar, /imu
      ↓
perception_node  → /perception/occ3d
slam_node        → /slam/localization_stateinfo, /dog_odom
planning_node    → /planning/path 或 /pnc_planner_path_with_time
control_node     → Unitree SDK2 / motor command
      ↓
robot

3.2 坐标系与局部地图

仿真和真实机器人都会不断做坐标转换。若机器人在世界坐标中的位姿为 \((x_r, y_r, \theta_r)\)，世界点 \(p_w=(x_w,y_w)\) 转到机器人局部坐标可写为：

\[ p_{ego} = \begin{bmatrix} \cos\theta_r & \sin\theta_r \\ -\sin\theta_r & \cos\theta_r \end{bmatrix} \left( \begin{bmatrix}x_w\\y_w\end{bmatrix} - \begin{bmatrix}x_r\\y_r\end{bmatrix} \right) \]

SenseBot 的 PNC simulator 正是在这个意义上从全局 heightmap 按机器人 pose 裁出局部 heightmap，再发布给规划/控制链路。

3.3 rosbag2 为什么重要

rosbag2 是 ROS2 的数据录制与回放机制。它让真实机器上的传感器、定位、规划输出变成可复现实验。生产中常见做法是：实机采集 bag，离线回放给感知/SLAM/规划节点，保存日志与轨迹，再把失败片段转成回归测试。

4. 本地项目一：AceAgent 仿真环境

主要证据：agent/server/agent/sandbox.py、agent/scripts/build_xian10th_sim_assets.py、agent/data/agent_sandbox/xian10th_real_fixture.json、agent/examples/agent_sandbox_cases_xian10th_real.jsonl、agent/ros2/agent_sandbox_bridge/。

4.1 这是工具层 sandbox，不是物理仿真

agent 的主系统是 OpenAI-compatible 对话服务，工具包括机器人控制、天气、地图、视觉分析、店铺下单等。其 sandbox 的重点是验证模型的“工具调用轨迹”：模型是否先查库存、再导航到小卖部、再播报、再下单、再检查订单、最后回到目标点。

sandbox.py 把工具分成三类：fixture-backed 查询工具、安全查询工具、执行类工具。默认情况下，查询工具从离线 fixture 返回，执行类工具被 sandbox 模拟，不会调用真实机器人、真实导航或真实下单 API。

层次实现用途
输入数据xian10th_real_fixture.json提供机器人状态、当前地图、点位、SKU、POI 等离线数据。
任务用例agent_sandbox_cases_xian10th_real.jsonl定义用户指令、允许工具、期望轨迹、位置检查、状态检查和禁止工具。
工具代理SandboxToolProxy拦截工具调用，决定真实调用或模拟返回，并更新虚拟机器人状态。
评估函数score_trace()从序列、参数、禁止工具、最终文本、状态、行为约束计算 loss。
ROS2 桥agent_sandbox_bridge把 2D sandbox 暴露成 ROS2 topic，便于接入 ROS2 生态。

4.2 xian_10th 场景是怎样搭出来的

build_xian10th_sim_assets.py 从只读地图/机器人列表中提取 xian_10th 地图，构建 fixture、用例和地图可视化。当前 fixture 中 preferred robot 是 xian_10，地图 id 为 181，包含 8 个真实点位：前台、贩卖机、茶水间、男卫生间、王老师办公室、充电桩、女卫生间、小卖部。

这类 fixture 的价值是可重复：同一个模型、同一批任务、同一个离线地图，可以稳定比较工具轨迹和 response time。

4.3 评估公式

score_trace() 的综合 loss 可抽象为：

\[ L = w_s L_{seq} + w_a L_{arg} + w_f L_{forbid} + w_t L_{text} + w_r L_{state} + w_b L_{behavior} \]

当存在状态检查时，源码使用的权重是 \(w_s=0.35, w_a=0.25, w_f=0.15, w_t=0.05, w_r=0.10, w_b=0.10\)。没有状态检查时，序列和参数权重分别提高到 0.40 和 0.30。

4.4 本地结果

在 data/agent_sandbox/runs/ 中，真实 xian_10th fixture 的两组摘要都显示 10 个用例全部通过。需要注意，“通过”表示 loss 没超过每个 case 的 max_loss，不是物理仿真里的碰撞安全通过。

模型用例数通过最大 loss平均响应时间p95
qwen-122b10100.1751843.595 ms3634.186 ms
qwen-35b10100.2251361.704 ms2999.764 ms
工程观察：interrupt_store_then_meeting_xian_10 被标注为真实 xian_10th 不支持，因为点位列表没有“会议室”。这是一个好的仿真设计信号：它没有伪造不存在的点位让用例看起来完美，而是保留 loss 和 unsupported reason。

4.5 ROS2 bridge 的作用

agent/ros2/agent_sandbox_bridge 是一个最小 ROS2 bridge：读取 xian10th_real_fixture.json，发布 /agent_sandbox/robot_pose 和 /agent_sandbox/state，订阅 /agent_sandbox/goal。输入可以是文本点位，也可以是 JSON 目标；如果目标点位存在，节点立即更新 2D pose。

/agent_sandbox/goal  -- std_msgs/String(JSON or text) --> xian10th_sim_node
xian10th_sim_node    -- geometry_msgs/Pose2D ------------> /agent_sandbox/robot_pose
xian10th_sim_node    -- std_msgs/String(JSON) -----------> /agent_sandbox/state

这一步的意义是把 Agent sandbox 从“Python 内部测试”推进到“ROS2 graph 中的一个可连接节点”。之后可以接 RViz、rosbag2、测试节点或上层调度器。

5. 本地项目二：SenseBot 仿真与部署环境

主要证据：19_sensebot_robotics_system/congq_sensebot/CLAUDE.md、README.md、Makefile、scripts/start_all.sh、scripts/setup_and_launch.sh、src/pnc/*simulator*、congq_sensebot_dlp/README.md、dlp_node.py、config/isaac.yaml。

5.1 SenseBot 是 ROS2 生产系统快照

SenseBot 主工程是面向 Unitree Go2/HG 四足机器人的 ROS2 自主导航系统。目标硬件包括 NVIDIA Jetson Orin/aarch64，支持 Ubuntu 20.04/ROS2 Foxy 与 Ubuntu 22.04/ROS2 Humble。构建和运行均要求在 Docker 容器内执行。

Sensors → Perception → SLAM → Planning → Control → Unitree SDK2 → Robot │ │ │ │ │ │ │ └─ 低层运动控制 │ │ └─ TEB / PNC / 轨迹 │ └─ /slam/odom_stateinfo, /slam/localization_stateinfo, /slam/nav_map └─ RealSense, Hesai/RSLiDAR, GNSS, IMU

5.2 构建与部署

构建链路使用 colcon build 和 Makefile 封装。x86 目标更像开发/回放环境，ARM 目标包含传感器驱动与机器人部署包。典型命令包括：

# 容器内执行
make x86_u22      # Ubuntu 22.04 / ROS2 Humble 开发构建
make arm_u22      # aarch64 / Jetson Orin 目标构建
./scripts/pack.sh aarch64

# 部署到 Go2 Orin 后
./scripts/start_all.sh
./scripts/stop_all.sh

start_all.sh 的职责包括停止旧进程、设置环境变量和校准、启动诊断、启动传感器、启动应用层节点、启动 voice agent、monitor 和 util 服务。setup_and_launch.sh 单独启动 statemachine、slam、perception、planning、control、device_control 等应用层节点。

5.3 传感器与运行时配置

start_sensor.sh 会读取 ~/config/config.sh 中的 robot_id、gnss_type、robot_model，设置 UNITREE_SDK2_DIR=/opt/unitree_sdk2，再启动 Hesai、M20 RSLiDAR、RealSense、GNSS、H30、RID 等节点。它还会检查特定设备或服务是否在线，例如 JT128 LiDAR、M20 multicast relay、RealSense USB 模式。

5.4 bag 回灌是生产仿真的主力

scripts/batch_bag_replay.sh 把每条回放命令包装成严格顺序：更新 calibration 软链接，start_all，执行 robot bag play，stop_all，归档日志，再用 SLAM SDK 绘制轨迹。它体现了生产测试的关键思想：真实数据回放比随机写一个 simulator 更能暴露传感器、SLAM 和规划的工程问题。

5.5 PNC 轻量 simulator

SenseBot 的 src/pnc 下有一个轻量级 simulator。它不是完整物理引擎，而是为了给规划/控制链路提供局部 heightmap 和机器人 odometry：

  • simulator.launch.py 声明全局/局部 heightmap 尺寸、分辨率、机器人初始 pose 和发布频率。
  • simulator_node.cpp 创建全局 heightmap，加入矩形障碍物，订阅 /pnc_planner_path_with_time，按轨迹时间戳线性插值机器人 pose。
  • simulator.cpp 支持创建、加载、保存全局 heightmap，并从全局图按 ego pose 裁出局部 heightmap。
/pnc_planner_path_with_time
      ↓
simulator_node: trajectory interpolation
      ↓
/simulator/robot_pose        → remap to /dog_odom
/simulator/local_heightmapa  → intended local height map for planning/control
工程观察：simulator.launch.py 中 remap 的源 topic 是 /simulator/local_heightmap，但 simulator_node.cpp 实际发布 /simulator/local_heightmapa；remap 目标还写成 /utlidar/height_map_arra。此外主 launch/sensebot.launch.py 在 SLAM include 附近存在明显语法断裂。报告只把这些作为本地快照的审阅发现，不假设当前目录可直接运行。

5.6 DLP 与 Isaac 模型在环

congq_sensebot_dlp 是基于 PyTorch Lightning 和 Hydra 的路径规划模型训练/评估框架。它提供了训练、评估、批量评估、指标聚合、ONNX 导出和 ROS2 推理节点。

README.md 的仿真测试流程显示：启动 isaaclab_dev conda 环境，source ROS2 Humble，构建 ros_ws，设置 ROS_DOMAIN_ID=60，运行 python dlp_node.py；另起容器运行 planning/control；最后在 isaac_go2_ros2 中运行 isaac_go2_ros2.py --livestream 2 --enable_cameras --scene scene_5/route_4。

dlp_node.py 的 ROS2 输入输出如下：

方向Topic / 消息作用
订阅/perception/occ3d_single / nav2_msgs/VoxelGrid占据栅格，转为 occ_grid 与 mask_camera。
订阅/slam/localization_stateinfo定位、速度、加速度、角速度，转为状态向量。
订阅/state_change导航 route 描述，解析后转到 ego 坐标。
发布planning_pred_traj / nav_msgs/Path发布模型预测的最佳轨迹。

ONNX 部署脚本 export_onnx.py 使用输入 occ_grid、mask_camera、route、state，输出 trajs、confidences、best_mode，并调用 onnx.checker.check_model 做导出校验。

5.7 感知 OCC 与仿真数据

congq_sensebot_perception 负责 occupancy / 3D 感知训练和部署。README 中包含 Docker 镜像、train_occ_sensebot.py、test_occ.py、可视化、deploy eval、数据结构和 OCC ground truth 命名规则。script/occ_infer/model_release/r30.3/README.md 还提供了 release 版 OCCDLP 的推理命令、视频/可视化保存参数和训练命令。

这说明 SenseBot 的模型生产流并不是“仿真环境单独存在”，而是由真实数据、OCC 训练、DLP 规划、ROS2 节点、bag 回灌和 Isaac 场景共同构成。

7. 机器人/机器狗仿真的生产力流程

7.1 从最小可复现开始

  1. 定义任务契约：用户指令、地图点位、允许工具、禁止工具、预期状态、成功指标。
  2. 做 fixture/sandbox：先用离线地图和模拟状态验证 LLM 或调度器是否会按正确顺序调用工具。
  3. 接 ROS2 bridge：把 sandbox 的状态和目标暴露成 topic，开始检查消息类型、topic 名和 launch 组织。
  4. 引入 bag 回灌：用真实传感器和定位数据驱动感知/SLAM/规划，避免只在 synthetic 场景中自洽。
  5. 模型在环：把 DLP、OCC、VLN/VLA 模型作为 ROS2 节点接入，记录输入输出和延迟。
  6. 物理仿真：用 Isaac/Gazebo/MuJoCo 检查传感器模拟、碰撞、足式动力学和控制闭环。
  7. 实机灰度：在低风险场景、低速度、可急停条件下部署，失败日志回灌到前面几层。

8. 方法对比与选择建议

目标优先环境原因不适合做什么
评估 LLM Agent 是否会正确用工具AceAgent sandbox成本低、可批量、可给轨迹 loss。不能证明物理安全、避障和运动控制正确。
检查 ROS2 模块通信ROS2 bridge / launch / rosbag2直接暴露 topic、message、QoS、启动顺序。不能自动覆盖传感器真实性和动力学。
回归真实道路/园区数据bag replay最接近线上问题，便于复现。不能探索没有采集过的新场景。
训练/验证感知与规划模型OCC/DLP 离线评估 + Isaac 模型在环既有指标又能接 ROS2 闭环。如果没有物理闭环，不能验证底盘动态。
机器狗 locomotion 和接触控制MuJoCo / Isaac Lab / Unitree RL Gym需要接触动力学和大量并行 rollouts。不擅长直接替代 ROS2 生产系统部署。
端到端产品部署Docker + colcon + pack + 实机灰度贴近 SenseBot 当前生产形态。风险高，必须前置 sandbox、bag、仿真验证。
建议路线：先用 agent 的 sandbox 建立任务级回归集，再把关键任务通过 ROS2 bridge 接到最小 ROS graph；随后用 SenseBot 的 bag replay 和 DLP/Isaac 流程做模型在环；最后再进入 Unitree 实机与 Docker 打包部署。这样每一层失败都有可回放证据。
